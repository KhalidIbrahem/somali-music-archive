# Browser DAW architecture in 2025–2026: audio engine, libraries, limits and proven patterns

Research notes compiled 2026-11-07 for the audio-engine decision of a Next.js/React/TypeScript browser DAW that already uses the Web Audio API with synthesised instruments, AudioWorklet recording and IndexedDB persistence. Every factual bullet carries its source; items marked **[background, pre-2023]** are older but still the canonical reference. Where the only evidence is a vendor post, a forum anecdote or a search snippet, it is labelled as such. Two primary documents could not be read in full (the HAW Hamburg thesis and the WAC 2025 disk-streaming paper, both image/glyph-encoded PDFs); what they contain is recorded under Gaps rather than guessed.

---

## Key question 1 — Web Audio API vs AudioWorklet vs WebAssembly DSP; sample-accurate scheduling; tempo, loop regions and count-in

### Takeaway
The proven 2025–2026 pattern is a three-tier engine: native Web Audio nodes for routing/gain/convolution, one or a few AudioWorklet nodes for anything custom (instruments, metering, recording), and WASM inside the worklet only when you port an existing C++/Rust codebase or need GC-free determinism — the one controlled benchmark found (WAC 2022) shows plain JS AudioWorklets are competitive with WASM and that per-sample WASM calls are the slow path. Timing is done by the look-ahead scheduler (timer in a Web Worker, 25–100 ms period, 100–150 ms look-ahead, every event stamped on `AudioContext.currentTime`), with the transport/tempo map living in the engine (openDAW keeps it in Rust on the audio thread); bounce is done with `OfflineAudioContext`.

### Cited Findings

**Render quantum, threads and budgets**
- The Web Audio API processes audio in blocks of 128 frames; at 48 000 frames/s all processing for one block (every `process()` call plus every native node) must finish in about 3 ms (128 × 1000 / 48000 = 2.67 ms); worklet code runs on "a dedicated real-time system thread", output is produced synchronously so the pipeline adds no buffering of its own; missed deadlines stutter; avoid non-deterministic work (allocation, promises), reuse typed arrays, prefer transferring ArrayBuffers; `MessagePort` allocates, `SharedArrayBuffer` enables lock-free programming — [Mozilla Hacks, Adenot/Tomlinson/Stevenson, 2020-05-07 — background](https://hacks.mozilla.org/2020/05/high-performance-web-audio-with-audioworklet-in-firefox/)
- `audioContext.currentTime` advances once per block ("every 128 samples", ≈2.9 ms at 44.1 kHz) and "returns the time of the next block that will be computed" — [IRCAM ISMM Web Audio tutorial, scheduling](https://ircam-ismm.github.io/webaudio-tutorials/scheduling/timing-and-scheduling.html)
- Chromium is shipping a configurable render quantum: an optional `renderSizeHint` on `AudioContext` and `OfflineAudioContext` (integer, `"default"` = 128 frames, `"hardware"` lets the UA choose but currently always returns 128 in Chromium); origin trial milestones 145–151, shipping target Chrome 153 (desktop, Android, WebView); intent posted 2026-07-23, three LGTMs 2026-07-27/29 — [blink-dev Intent to Ship: Configurable render quantum](https://groups.google.com/a/chromium.org/g/blink-dev/c/i4c1unRSmcE); the trial was extended in April 2026 "due in part to issues which were uncovered by the Origin Trial itself" — [blink-dev Intent to Extend Experiment](https://groups.google.com/a/chromium.org/g/blink-dev/c/MlLqosTB0cQ); the spec PR sets the valid range to 1 sample … 6 seconds and debates renaming the attribute `renderQuantumSize` — [WebAudio/web-audio-api PR #2667](https://github.com/WebAudio/web-audio-api/pull/2667)

**JS vs WASM inside AudioWorklet (the only controlled benchmark found)**
- Roma, "Comparing approaches for new AudioWorklets", WAC 2022: a polyBLEP sawtooth, a sine and a biquad low-pass were implemented in pure JS, C++/Emscripten (per-sample call and whole-128-buffer call) and AssemblyScript (both), measured as the maximum number of worklets before the audio glitched (quantised to steps of 50) on a 2021 M1 Pro MacBook Pro with Firefox 99 and Chrome 100; findings: "Chrome seems to favour the performance of native AudioNodes, in Firefox the JavaScript implementations approach the native ones"; "especially in Firefox, the pure JS version stands well against WebAssembly implementations"; "the buffer versions are always faster" than per-sample WASM calls because of per-call overhead; AssemblyScript results "mixed"; "Emscripten/C++ using a buffer seems to be the safest bet for WebAssembly"; "WebAssembly is clearly not a magic bullet that makes code automatically faster"; WASM's clear advantage is that it has no garbage collector; a single hardware/OS combination was tested and the numeric results are only in figures — [Zenodo record 6767468, PDF WAC_2022_paper_46](https://zenodo.org/records/6767468)
- Karplus-Strong stress tester (Schaedler): many K-S strings in AudioWorklet nodes in JS and in Rust/WASM; per-string data sent to the GUI 60×/s over `MessagePort` or `SharedArrayBuffer`; the author reports that `MessagePort` "allocates memory, which triggers garbage collection", that SAB avoids this, that JS is "surprisingly fast in modern browsers" after JIT warm-up (early glitches until optimised), and recommends simulating many strings in one worklet node ("100 strings per worklet"); Firefox and Chrome only, Safari unsupported; SAB in Firefox needed Nightly + `bypassCOOP_COEP.insecure.enabled`; no numeric results in the README — [jackschaedler/karplus-stress-tester](https://github.com/jackschaedler/karplus-stress-tester)
- HAW Hamburg bachelor thesis (Sascha Knapp, issued 2023-02-08, keywords Web Audio API, AudioWorklet, SharedArrayBuffer, Web Audio Modules, WebAssembly, DAW): a browser DAW engine using AudioWorklet + SharedArrayBuffer + Web Workers for disk streaming, WAM + WASM plugins, evaluated with the Firefox Profiler against an `AudioBufferSourceNode` design and comparing WASM vs JS processing; concludes browser DAWs "can be a viable alternative to native DAWs" — [HAW reposit handle 20.500.12738/16337](https://reposit.haw-hamburg.de/handle/20.500.12738/16337?mode=full)
- openDAW's engine (the most complete open-source reference): a Rust cargo workspace compiled to WebAssembly; `studio-core-wasm` "instantiates `engine.wasm`, and exposes it as an AudioWorklet processor"; 27 position-independent device side modules linked into shared memory and called via `call_indirect`; `talc` allocator, size-optimised release profile with hot DSP crates at `opt-level = 3`; the audio thread "never reads main thread state directly" but is fed a mirror of the box graph via transactions; analysis, time-stretching, BPM detection, ONNX inference, OPFS and user scripts run in Workers; `LiveStream` moves meters/spectra/note activity from the audio thread to the UI "without locks"; the WASM engine is the default "since mid 2026" with a TypeScript engine (`studio-core-processors`) as alternative; the Rust `dsp` crate must match the TS `lib-dsp` "float for float" — [openDAW introduction.md](https://raw.githubusercontent.com/andremichelle/opendaw/main/introduction.md); building it needs Rust ≥ 1.82 nightly with `rust-src`, target `wasm32-unknown-unknown`, optional `wasm-opt` — [openDAW README](https://github.com/andremichelle/opendaw)
- openDAW performance notes (2026-04-11): offline `/performance` benchmarks run each device in a Worker via `OfflineEngineRenderer` with JIT warm-up and the main AudioContext suspended, reporting render time, marginal cost vs an empty engine and per-quantum cost; optimisations listed: modulo → bitmask indexing in the resampler, flattened reverb delay arrays, "zero allocations per render quantum" in `BlockRenderer`, regex parsing moved out of the scripted devices' hot path, UI animation frames throttled from 120 fps to ~60 fps; no absolute CPU numbers are given — [openDAW docs/performance.md](https://raw.githubusercontent.com/andremichelle/opendaw/main/docs/performance.md)
- Vendor view (Superpowered, undated, references 2023): "major online audio applications" use a Web Audio graph with WASM DSP in AudioWorklets; the AudioWorklet scope has no Fetch API; Firefox lagged on ES-module `import` inside worklet scripts; caniuse coverage "around 94%" — vendor claim, no evidence offered — [superpowered.com](https://superpowered.com/riding-the-latest-waves-on-the-web)
- Ableton's Learning Synths is a Max patch exported with RNBO to WebAssembly; "the audio engine relies on WebAssembly and Audio Worklets", the UI is Node/TypeScript/HTML/CSS and the synth is "treated like a single JSON asset" (Jack Schaedler) — [Cycling '74 RNBO case study](https://rnbo.cycling74.com/explore/learning-synths-and-rnbo)
- JUCE staff (dave96, 2021-12-20) on running Tracktion Engine in a browser: WASM via Emscripten is the ideal route but "WASM had been struggling with C++ threads over security concerns"; JUCE had a long-term plan with no date — [JUCE forum thread](https://forum.juce.com/t/hints-for-using-tracktion-engine-in-a-web-app-front-end/49319)

**Look-ahead scheduling and transport**
- Chris Wilson, "A tale of two clocks" **[background, undated on page]**: a JS timer (setTimeout every 25 ms) queues notes up to 100 ms ahead on the audio clock; overlapping windows survive a 50 ms main-thread stall; OS audio buffer latency "from a few milliseconds to around 50 ms" must fit inside the look-ahead; a tempo change takes effect only after already-queued notes (≈100 ms in the metronome); a 250 ms/200 ms variant is "less resilient to tempo changes"; use `requestAnimationFrame` reading the audio clock for visuals — [web.dev/articles/audio-scheduling](https://web.dev/articles/audio-scheduling)
- IRCAM tutorial refinement: period must be strictly shorter than look-ahead (their `LookaheadScheduler` uses period 0.05 s, look-ahead 0.1 s); events live in a time-sorted priority queue; `tick` schedules everything with `time < now + lookahead`; stopping/seeking means removing queued events — [IRCAM ISMM tutorial](https://ircam-ismm.github.io/webaudio-tutorials/scheduling/timing-and-scheduling.html)
- Tone.js defaults: `clockSource: "worker"`, `latencyHint: "interactive"`, `lookAhead: 0.1`, `updateInterval: 0.05`; "context.updateInterval + context.lookAhead gives you the total latency between scheduling an event and hearing it"; `lookAhead = 0` gives lowest latency and forces `updateInterval` 0.01 — [Tone.js Context.ts](https://raw.githubusercontent.com/Tonejs/Tone.js/dev/Tone/core/context/Context.ts); the Ticker builds a Web Worker from a Blob URL running a recursive `setTimeout` that posts `'tick'`, falls back to main-thread `setTimeout` if worker creation throws, and clamps the interval to `max(128/sampleRate, 0.001)` s — [Tone.js Ticker.ts](https://raw.githubusercontent.com/Tonejs/Tone.js/dev/Tone/core/clock/Ticker.ts); Transport supports tempo automation (`bpm.rampTo(800, 10)`), `Tone.Loop`, and relies on `standardized-audio-context` shims; 14.9k stars, MIT — [Tonejs/Tone.js](https://github.com/Tonejs/Tone.js)
- Strudel's clock (`zyklus.mjs`): `duration = 0.05` s per cycle tick, `interval = 0.1` s between callbacks, `overlap = 0.1` s (falls back to `interval/2`), `minLatency = 0.01`, phases rounded to 1e-4 s, window `lookahead = t + interval + overlap`, plain `setInterval` (injectable), no Worker — [strudel/packages/core/zyklus.mjs](https://codeberg.org/uzu/strudel/raw/branch/main/packages/core/zyklus.mjs); the scheduler (`cyclist.mjs`) adds a fixed `latency = 0.1` s trigger offset, maps cycles→seconds from checkpoints rather than accumulating (drift control), and on a tempo (`cps`) change inside a tick resets the checkpoint and re-queries the remainder of the tick — [strudel/packages/core/cyclist.mjs](https://codeberg.org/uzu/strudel/raw/branch/main/packages/core/cyclist.mjs); the Web Audio binding passes `getTime: () => ctx.currentTime` and `initAudioOnFirstClick()` — [@strudel/webaudio README](https://cdn.jsdelivr.net/npm/@strudel/webaudio@1.3.0/README.md); the output `superdough(value, deadline, duration)` takes an absolute audio-clock deadline — [superdough on npm](https://npmjs.com/package/superdough)
- Elementary's position: anything pushed from JS "will only be applied at the beginning of the next audio block" (blocks hold "a few (or tens of) milliseconds"); sample-accurate behaviour comes from expressing the modulation inside the graph — [Elementary: Sample-accurate rendering](https://www.elementary.audio/docs/guides/Sample_Accurate_Rendering)
- WAM 2.0 plugins expose `scheduleEvents()` with timestamps "relative to `AudioContext.currentTime`" (untimed events run ASAP), `clearEvents()`, `getCompensationDelay()`, and warn that main-thread parameter getters/setters "should not be used in time-critical situations" — [webaudiomodules/api](https://github.com/webaudiomodules/api)
- Transport in openDAW: a Rust `transport` crate "handles playback position, tempo map, and loop handling"; `lib-dsp` provides PPQN and SMPTE time bases and tempo maps — [openDAW introduction.md](https://raw.githubusercontent.com/andremichelle/opendaw/main/introduction.md)
- Georgia Tech talk "Alternatives to Lookahead Audio Scheduling" contrasts look-ahead with all-at-once scheduling and OfflineAudioContext pre-rendering ("A Tale of No Clocks") — search snippet only; the repository page returned 404 on fetch — [repository.gatech.edu](https://repository.gatech.edu/entities/publication/ac112129-16e6-44b3-872b-ed063a32a5df)

**Offline rendering (bounce/mixdown)**
- `OfflineAudioContext(numberOfChannels, length, sampleRate)` renders "as fast as it can" into an `AudioBuffer`; `suspend(time)`/`resume()` allow chunked rendering; Baseline widely available since April 2021 — [MDN OfflineAudioContext](https://developer.mozilla.org/en-US/docs/Web/API/OfflineAudioContext)
- `Tone.Offline(callback, duration, channels = 2, sampleRate)` swaps the global context for an `OfflineContext`, runs the callback (the transport must be started inside it), then restores the live context while rendering completes — [Tone.js Offline.ts](https://raw.githubusercontent.com/Tonejs/Tone.js/dev/Tone/core/context/Offline.ts)
- spessasynth_lib exports audio "using OfflineAudioContext" and can render each MIDI channel and the effects separately (stems) — [spessasynth_lib](https://github.com/spessasus/spessasynth_lib); wavelet advertises "Faster offline rendering" — [ryohey/wavelet](https://github.com/ryohey/wavelet)

**Timer throttling (why the scheduler timer belongs in a Worker)**
- Chrome 88 intensive throttling: when a page has been hidden > 5 minutes, the timer chain count is ≥ 5, the page has been silent ≥ 30 s and WebRTC is not in use, timers are "check[ed] … once per minute"; audible sound in the last 30 s exempts the page but "a silent audio track doesn't count"; Workers are not mentioned — [Chrome Developers: Timer throttling in Chrome 88](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)
- Chrome 57 **[background]**: background pages get a timer budget after 10 s; pages playing audible audio are exempt "when and only when Chrome shows the audio icon", silent streams do not qualify — [Chrome Developers: Background tabs in Chrome 57](https://developer.chrome.com/blog/background_tabs)

### Inferences
- For a Next.js DAW that already has synthesised instruments in Web Audio, the Roma result means there is no performance reason to rewrite DSP in WASM; move to WASM only for (a) porting existing C++/Rust/Faust code, (b) GC-free determinism in a large engine, or (c) hosting WebCLAP/WAM plugins. If WASM is used, call it once per 128-frame block, never per sample.
- One engine worklet (openDAW, wavelet, Elementary, Glicol all do this) beats many small worklets: fewer cross-thread hops and the stress tester's "many strings per node" recommendation.
- Count-in and loop regions are engine-side transport features (position/tempo map in the engine thread, as openDAW does); the UI only sends transactions. No browser-specific count-in implementation write-up was found; BandLab's product doc confirms count-in exists as a feature (see Q2).
- Tempo changes with a look-ahead scheduler are only as responsive as the look-ahead (≈100 ms); for live tempo nudging keep look-ahead ≤ 100 ms and keep the timer in a Worker (Tone.js) so background throttling does not stall it. Strudel's checkpoint-based cycle→seconds mapping is the cleanest reference for tempo maps that change mid-tick.

### Gaps
- No public numeric table of JS vs WASM AudioWorklet throughput beyond Roma's figures (which are in images only); the HAW thesis holds a Firefox-Profiler comparison but its PDF text could not be extracted here.
- No authoritative measurement of AudioWorklet behaviour in Safari vs Chrome vs Firefox on current (2026) versions; Roma used Firefox 99/Chrome 100 and excluded Safari.
- `AudioRenderCapacity`/`renderCapacity` shipping status could not be confirmed (searches only surfaced the render-quantum intent).
- Count-in / punch-in / loop-record engine design: no engineering write-up found for any browser DAW.

## Key question 2 — Round-trip latency, recording, latency compensation, monitoring; iOS Safari

### Takeaway
Measured browser round-trip latency is 40–65 ms on laptops with default settings and ~14–20 ms only when `echoCancellation/noiseSuppression/autoGainControl` are off and `latencyHint` is 0 (Firefox ≈14 ms, Chrome ≈19 ms but jittery); Safari measured ~100 ms on a 2021 MacBook Pro. Commercial browser DAWs that compensate from estimates mis-align by 10–190 ms, whereas a measured loopback calibration (MLS cross-correlation) gets within ~1 ms — so build a one-click calibration and store the per-device offset. iOS Safari needs `navigator.audioSession.type = "playback"` (silent switch), a user-gesture resume, and defensive handling of route/sample-rate changes and PWA backgrounding; echo-cancelled capture currently crackles on iOS 26.2–27.

### Cited Findings

**Measured round-trip latency**
- Jeff Kaufman, 2021-02-02, 2016 15" MacBook, macOS 11.1, beep→mic loopback via an AudioWorklet: defaults Chrome ≈67 ms, Firefox ≈55 ms; with `latencyHint: 0` and `getUserMedia({latency: 0, echoCancellation: false, noiseSuppression: false, autoGainControl: false})` Chrome ≈19 ms, Firefox ≈14 ms; Chrome's `MediaTrackSettings.latency` always reported 0.01; Firefox's `outputLatency` was "less than half the true end-to-end latency"; Bluetooth headsets under-report; conclusion: no API reports end-to-end latency accurately, so measure it — [jefftk.com/p/browser-audio-latency](https://www.jefftk.com/p/browser-audio-latency)
- Jeff Kaufman, 2020-05-06/07, 2017 MacBook Pro, macOS 10.14.6, tap-echo method: defaults Reaper 15 ms, Firefox 62 ms, Chrome 124 ms (Chrome ranged 77–163 ms); after `latencyHint: 0` + EC/NS/AGC off: Reaper 11 ms, Firefox 14 ms, Chrome 19–41 ms (mostly 19, up to 30 ms); Safari untested (no AudioWorklet then) — [jefftk.com/p/audioworklet-latency-firefox-vs-chrome](https://www.jefftk.com/p/audioworklet-latency-firefox-vs-chrome)
- MLS loopback method (Gil Panal, Richard, David, WAC 2025, DOI 10.5281/zenodo.17642262; cross-correlation of a maximum-length sequence, +18 dB peak-to-rest threshold, 100 runs): HP Ubuntu 22.04 — Chrome 64.50 ± 7.94 ms, Chromium 64.15 ± 8.21, Firefox 65.69 ± 0.00; Lenovo Windows 10 — Edge 60.82 ± 6.06, Chrome 62.84 ± 2.44, Firefox 104.65 ± 0.00; MacBook Pro 2021 — Safari 100.02 ± 0.00, Chrome 52.33 ± 1.14, Firefox 38.89 ± 0.00; Firefox had zero jitter everywhere, Chromium browsers ~8 ms std-dev on Ubuntu; Safari needed special handling for low input gain — [gilpanal/weblatencytest](https://github.com/gilpanal/weblatencytest)
- Same study, residual misalignment of recordings in online DAWs after their own compensation (Firefox, ms; negative = recording placed too early): Soundtrap −182.77 / −179.08 / −194.24 (its estimates 249 / 314 / 232 ms); Amped Studio −11.38 / −7.96 (estimates 69 / 146); BandLab −73.85 / −14.56 / +0.73 (estimates 139 / 147 / 38); WAM-online studio +58.66 / +53.73 / +20.66; the authors' MLS-calibrated "Hi-Audio" +0.68 / +0.48 / +1.09 — [gilpanal/weblatencytest](https://github.com/gilpanal/weblatencytest)
- Soundtrap offers a "Latency Calibration" run from the Voice & Mic track ("calibrate your mic to Soundtrap's settings … new recordings will now align correctly with the beat"), a "Low latency mode" toggle that turns off "some of the high-quality audio settings … that tend to increase latency", and a Mac desktop app to reduce browser latency — [Soundtrap support: Latency Calibration](https://support.soundtrap.com/hc/en-us/articles/25549534050962-Latency-Calibration), [Soundtrap support: Latency](https://support.soundtrap.com/hc/en-us/articles/26663690434066-Latency), [Soundtrap blog](https://soundtrap.com/content/blog/how-to-fix-recording-latency-in-your-daw)
- BandLab's Mix Editor has a count-in ("Adds a metronome count before recording begins") — third-party guide — [audeobox BandLab guide](https://www.audeobox.com/learn/bandlab/bandlab-getting-started/); a 2020 forum post reports BandLab recording latency of "100–200 ms" and "variable and inconsistent" — anecdotal — [djangobooks forum](https://djangobooks.com/forum/discussion/17742/Contact)
- Browser APIs for latency: `AudioContext.baseLatency` (Chrome 58, Firefox 70, Safari 14.1), `outputLatency` (Chrome 102, Firefox 70, Safari 18.4; MDN marks it Baseline 2025 "since March 2025"), `latencyHint` constructor option (Chrome 58, Safari 14.1, Firefox not supported), `setSinkId()`/`sinkId` Chrome 110 only — [mdn/browser-compat-data AudioContext.json](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/AudioContext.json), [MDN outputLatency](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/outputLatency); MDN's `baseLatency` example shows 0.00 s for `"interactive"` and 0.15 s for `"playback"` and notes the browser may ignore the hint — [MDN baseLatency](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/baseLatency)
- Safari: AudioWorklet shipped unprefixed in Safari 14.1 (2021-04-26) and iOS 14.5 — [WebKit blog, Safari 14.1](https://webkit.org/blog/11648/new-webkit-features-in-safari-14-1), [web-features: audio-worklet](https://web-platform-dx.github.io/web-features-explorer/features/audio-worklet)
- Safari capture quirk: with only a MediaStream and an AudioWorkletNode in the graph, WebKit requests a 20 ms capture buffer (`MediaSessionManagerCocoa.mm`) that is misaligned with 128-frame render quanta and "glitch[es] on speakers"; filed 2023-03-15, still NEW — [WebKit bug 253952](https://bugs.webkit.org/show_bug.cgi?id=253952)
- "Recording audio through an AudioWorklet produces corrupted data" (NEW, 2023) and "Glitches in AudioWorklet playback" (NEW, 2023) remain open in WebKit — [WebKit AudioWorklet bug list](https://bugs.webkit.org/buglist.cgi?quicksearch=AudioWorklet&order=changeddate%20DESC)
- Ableton Link's README states the general rule: "Audio output latency should be added to system time values before they are passed to Link methods" — [Ableton/link](https://github.com/Ableton/link)

**iOS Safari specifics**
- Silent switch: Web Audio used the ringer channel while `<audio>/<video>` use the media channel, so the side switch muted Web Audio; WebKit's reply (2024-09-25): since iOS 17 set `navigator.audioSession.type = "playback"`; the default `"ambient"` type is muted when the phone is muted; bug closed CONFIGURATION CHANGED — [WebKit bug 237322](https://bugs.webkit.org/show_bug.cgi?id=237322); `AudioSession`/`AudioSession.type` support: Safari 16.4 (iOS mirrors), Chrome not supported, Firefox preview only; experimental — [mdn/browser-compat-data AudioSession.json](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/AudioSession.json); types `auto, playback, transient, transient-solo, ambient, play-and-record`, states `active/interrupted/inactive` with `statechange` — [MDN AudioSession](https://developer.mozilla.org/en-US/docs/Web/API/AudioSession)
- Route/sample-rate change: switching to a Bluetooth speaker distorts and speeds up Web Audio on iPhone/iPad; WebKit's Jer Noble attributes it to "the sample rate of the output device changing when a different route … is selected"; a fix landed in STP 178 (2023-09) but the bug is still NEW and a 2024-07-26 comment reports the same with `AudioWorkletNode` at 48 kHz (workaround: `AudioBufferSourceNode`) — [WebKit bug 258864](https://bugs.webkit.org/show_bug.cgi?id=258864)
- Backgrounded home-screen PWA: AudioContext silent after returning from background even when `state === "running"` (~1 in 10); on iOS 26.0 Web Audio worked only on the first PWA run and `resume()` never returned; iOS 26.2 beta 3 "appears to have been fixed" on one device; status NEW (2025-04 → 2025-11) — [WebKit bug 291892](https://bugs.webkit.org/show_bug.cgi?id=291892); related: "WebAudio goes silent when closing another tab that had audio" — [WebKit bug 276687](https://bugs.webkit.org/show_bug.cgi?id=276687)
- Echo-cancelled capture: on iOS 26.2–27 any output "crackles while getUserMedia mic capture with echo cancellation is active"; `echoCancellation: false` stops it but routes output to the earpiece at much lower volume; `applyConstraints` did not help, `replaceTrack` with a non-EC track did; reported 2026-10-04, NEW, severity Major — [WebKit bug 326286](https://bugs.webkit.org/show_bug.cgi?id=326286)
- Older iOS sample-rate confusion (AudioContext defaulting to 48 kHz and sounding distorted; close-and-recreate workaround) — **[background, iOS 6–9 era]** — [WebKit bug 154538 thread](https://lists.webkit.org/pipermail/webkit-unassigned/2016-February/705819.html), [ios-safe-audio-context](https://npmjs.com/package/ios-safe-audio-context)
- Autoplay: Chrome's policy covers Web Audio since Chrome 71 (media elements since 66); an `AudioContext` created before a user gesture is created `"suspended"` and must be `resume()`d in a click handler; desktop Media Engagement Index can pre-authorise sites — [Chrome Developers: Autoplay policy](https://developer.chrome.com/blog/autoplay); Firefox blocks Web Audio until sticky activation (`media.autoplay.block-webaudio` default true); `navigator.getAutoplayPolicy("audiocontext")` returns `allowed/allowed-muted/disallowed` — [MDN Autoplay guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)
- Vendor anecdote: "~350 MB" is the practical memory before an iPhone Safari tab crashes (undocumented, Superpowered's observation) — [superpowered.com](https://superpowered.com/riding-the-latest-waves-on-the-web)

### Inferences
- Default `getUserMedia` routes through the browser's echo canceller/APM, which is where most of the 40–60 ms comes from; a DAW should request EC/NS/AGC off for instrument tracks and offer EC only for voice-chat style use — but on iOS 26.2–27 the EC path currently crackles and the non-EC path changes the output route, so give iOS users an explicit choice and test on device.
- Because `outputLatency`/`baseLatency` under-report (Kaufman) and app-side estimates mis-align by 10–190 ms (weblatencytest), the robust pattern is: play a known signal (click or MLS) through the speakers or a loopback cable, record it, cross-correlate, store the offset per input/output device pair, and shift recorded clips by that amount; re-measure when the device list or `outputLatency` changes (Kaufman's "even an imprecise value is useful if it changes").
- Input monitoring through the browser adds the full round trip (≥14–20 ms best case, ~100 ms Safari); recommend direct hardware monitoring (interface/headphones) and offer browser monitoring only as an opt-in with the measured latency shown.
- Firefox's zero jitter vs Chromium's ~8 ms std-dev means per-take compensation is stable in Firefox but may need per-session re-measurement in Chrome.

### Gaps
- No 2025–2026 measurements of Safari input latency on iOS (only a macOS Safari figure of ~100 ms).
- No sources on punch-in, take lanes or comping implementation in any browser DAW; AudioMass documents multitrack recording to armed channels with crossfades and bounce but not comping — [pkalogiros/AudioMass](https://github.com/pkalogiros/AudioMass).
- The Soundtrap engineering paper (Lind & MacPherson: Web Audio + Web MIDI + WebRTC, contributing lower-latency code to Chromium) could not be fetched (core.ac.uk 403); known only from a search snippet.
- Whether AudioWorklet is exempt from Chrome's background-tab throttling is not documented in the sources found (the real-time thread is separate, but main-thread timers feeding it are throttled unless audio is audible).

## Key question 3 — Instruments in the browser: sample players, physical modelling, synthesis libraries, WAM 2.0, oud and frame drum

### Takeaway
Sample-based GM/SoundFont playback is a solved problem with several maintained options (smplr and WebAudioFont on native nodes; spessasynth_lib, wavelet and FluidSynth-WASM as single-worklet synths; sfizz-webaudio for SFZ, Chrome-only), while synthesis libraries split into JS-graph (Tone.js), declarative WASM engines (Elementary, Glicol) and compile-to-WASM DSLs (Faust, RNBO). Plugin interchange is WAM 2.0 (AudioWorklet-based, 40+ plugins, iOS Safari support) and, since October 2026, WebCLAP (CLAP compiled to WASM, hosted by openDAW). For an oud, the sourced recipe is extended Karplus–Strong per course plus a commuted body impulse response; for a frame drum, modal synthesis as in Faust's `djembe` — no browser-specific oud or frame-drum implementation was found.

### Cited Findings

**Sample players / SoundFont / SFZ**
- smplr: "a collection of sampled instruments for Web Audio API ready to be used with no setup required"; TypeScript; its `Soundfont` player loads Benjamin Gleitzman's pre-rendered soundfonts by default; pre-1.0 ("features are considered unstable until v1.0"), last push 2026-03-24; the "modern replacement of soundfont-player" (archived) — [smplr on npm](https://npmjs.com/package/smplr), [danigb/soundfont-player](https://github.com/danigb/soundfont-player)
- WebAudioFont: GM instruments as JS preset files; `queueWaveTable(audioContext, target, preset, when, pitch, duration, volume, slides)` returns an envelope wrapping an `AudioBufferSourceNode`; "thousands of instrument[s]" derived from GeneralUserGS.sf2 and FluidR3.sf2 with 5–10 variants each; GPL-3.0 — [surikov/webaudiofont](https://github.com/surikov/webaudiofont)
- spessasynth_lib (v4.4.0, Apache-2.0): SF2/SF3/DLS/MIDI TypeScript library; `WorkletSynthesizer` "Runs in a separate thread for maximum performance!" and "Does not stop playing even when the main thread is frozen!"; convolver reverb and Yamaha XG effects; export via `OfflineAudioContext` incl. per-channel split rendering; writes MIDI/SF2/SF3 — [spessasus/spessasynth_lib](https://github.com/spessasus/spessasynth_lib); its core claims to be "the first (to my knowledge) JavaScript SoundFont synth with full modulator support", DLS Level 1 and 2, requires a WASM-capable JS environment — [spessasus/spessasynth_core](https://github.com/spessasus/spessasynth_core)
- wavelet (ryohey, MIT): "SoundFont Player built with AudioWorkletProcessor", "The single AudioWorkletProcessor which plays midi"; wavetable synth; "Never stops the UI thread"; "Ability to specify playback timing to prevent rhythm disruptions"; multi-channel; faster offline rendering — [ryohey/wavelet](https://github.com/ryohey/wavelet)
- js-synthesizer: "WebAssembly (wasm) version of FluidSynth" with `AudioWorkletNodeSynthesizer`; SF3 needs the libsndfile build (`libfluidsynth-2.4.6-with-libsndfile.js`); BSD-3-Clause library, LGPL-2.1 libfluidsynth — [jet2jet/js-synthesizer](https://github.com/jet2jet/js-synthesizer)
- SFZ: sfizz-webaudio is an "HTML/JavaScript/WebAssembly front-end for the sfizz engine" supporting only generators and embedded samples, loading all files into memory (virtual FS), live demo "requires Chrome or one of its derivatives" — [sfztools/sfizz-webaudio](https://github.com/sfztools/sfizz-webaudio); sfz-web-player is a pure JS/TS Web Audio SFZ player (CC0-1.0) — [sfzlab/sfz-web-player](https://github.com/sfzlab/sfz-web-player/blob/main/README.md)
- Signal (the open-source MIDI editor) ships "Basic Sound Quality" and "No Effects" and runs on Web Audio + AudioWorklet + Web MIDI — [ryohey/signal](https://github.com/ryohey/signal), [Signal ARCHITECTURE.md](https://raw.githubusercontent.com/ryohey/signal/main/ARCHITECTURE.md)

**Synthesis libraries and DSLs**
- Tone.js: "makes extensive use of the native Web Audio Nodes" (GainNode, WaveShaperNode …), audio-rate `Signal`s with `rampTo`, no AudioWorklet in the README; MIT; 14.9k stars — [Tonejs/Tone.js](https://github.com/Tonejs/Tone.js)
- Elementary: declarative functional graph ("Describe your audio process as a function of your application state"); `@elemaudio/core` (graph rendering and reconciliation), `@elemaudio/web-renderer` ("Elementary will construct an AudioWorkletNode in which the Elementary runtime operates"; `render()` returns `RenderStats`; samples go into a virtual file system as `Float32Array`s via `processorOptions.virtualFileSystem`/`updateVirtualFileSystem()`; `el.meter`/`el.snapshot` events), `@elemaudio/offline-renderer` for Node; "Elementary is MIT licensed"; 519 stars — [elemaudio/elementary](https://github.com/elemaudio/elementary), [web-renderer docs](https://www.elementary.audio/docs/packages/web-renderer); it compiles its JUCE-based C++ engine to WASM — [WAC 2022 paper 56](https://zenodo.org/record/6767578/files/WAC_2022_paper_56.pdf)
- Glicol: Rust parser and engine, ported to browsers with "WebAssembly, AudioWorklet and SharedArrayBuffer"; goal "Near-native, garbage-collection-free and memory-safe"; LCS-based graph diffing for live updates; `meta` node for per-sample code; MIT; "still highly experimental" — [chaosprint/glicol](https://github.com/chaosprint/glicol)
- Faust: `faustwasm` ships `libfaust-wasm` (compiler in the browser), `faust2wasm` with `-poly`, `-standalone`, `-pwa`; `createFaustNode` picks mono/poly from metadata; AudioWorklet primary, ScriptProcessor fallback for "older Safari versions"; polyphonic nodes expose `getNumActiveVoices()`; MIDI enabled from metadata — [grame-cncm/faustwasm](https://github.com/grame-cncm/faustwasm); `faust2webaudio` is archived — [grame-cncm/faust2webaudio](https://github.com/grame-cncm/faust2webaudio)
- RNBO (Cycling '74) exports Max patches to WASM for the web; used by Ableton Learning Synths — [RNBO case study](https://rnbo.cycling74.com/explore/learning-synths-and-rnbo)
- Chrome Music Lab experiments use "Web Audio API, WebRTC, WebMIDI, Tone.js, and more"; the repo was archived 2026-04-19 — [googlecreativelab/chrome-music-lab](https://github.com/googlecreativelab/chrome-music-lab)

**Plugin standards**
- WAM 2.0 (webaudiomodules.com): "a WAM is identified by a single URI" and can be loaded dynamically across websites; C/C++ code can be cross-compiled to WASM "and reuse a minimal set of features from the WAM SDK"; when host and plugins are AudioWorklets the framework communicates "without crossing the audio thread barrier" using SharedArrayBuffers and a ring buffer; "over 40 WAM2 plugins" in the community repo; "Works in all major browsers including iOS Safari"; examples in JS, TypeScript, React, Faust and C++ — [WAM docs intro](https://www.webaudiomodules.com/docs/intro)
- WAM API (v2 branch): `WebAudioModule` (static `createInstance`, `createAudioNode`, `createGui/destroyGui`), `WamDescriptor` with `hasAudioInput/Output`, `hasMidiInput/Output`, `hasAutomationInput/Output`, `hasMpe…`, `hasOsc…`, `hasSysex…`; `WamNode` with `getState/setState`, `getParameterInfo/Values`, `scheduleEvents`, `clearEvents`, `connectEvents/disconnectEvents`, `getCompensationDelay`; `WamProcessor` registers via `webAudioModules.addWam`; `WamEnv` singleton on the audio thread; `WamGroup` needs a `groupId` and a "secret" `groupKey` — [webaudiomodules/api](https://github.com/webaudiomodules/api); SDK: plugin = `index.js` exporting a `WebAudioModule` subclass whose only required method is `async createAudioNode(options)` (can return a `CompositeNode`) plus `gui.js` exporting `createElement(plugin)`; nodes are "bypassed by default" — [webaudiomodules/sdk](https://github.com/webaudiomodules/sdk); plugin groups receive MIDI together or share one parameter set (WAC 2022 guitar-rack demo) — [Zenodo 6769098](https://zenodo.org/record/6769098); a 2025 JAES retrospective "Ten Years of Web Audio Modules" exists (paywalled) — [AES e-library 23110](https://aes2.org/publications/elibrary-page/?id=23110)
- Amped Studio adopted WAM in 2018 (OBXD, DEXED free; Augur first commercial WAM) and was "developed within the new Web Assembly browser technology", then Chrome/Vivaldi/Opera only — [KVR, 2018-11-01](https://www.kvraudio.com/news-print.php?id=43058)
- WebCLAP/WCLAP: "a CLAP module compiled to a WebAssembly module" exporting `clap_entry`, packaged as `.wclap` directories with `module.wasm`; may import WASI; threads via wasi-threads; GUI via CLAP's webview extension (name varies across sources); `wclap-bridge` runs the same WASM in native DAWs via Wasmtime at "approximately 1.5x the CPU of the corresponding native builds" — [WebCLAP GitHub org](https://github.com/WebCLAP), [WebCLAP/browser-test-host](https://github.com/WebCLAP/browser-test-host); openDAW announced WebCLAP hosting on 2026-10-08 with OB-Xf (Surge Synth Team), Pro54 (Cmajor), Signalsmith "Basics", and a JUCE porting kit; plugins run in-browser with no helper app and travel with project bundles — [openDAW newsletter](https://buttondown.com/opendaw/archive/opendaw-now-runs-webclap-plugins/); the openDAW cloud lists 21 WebCLAP plugins — [openDAW README](https://github.com/andremichelle/opendaw)

**Plucked string (oud) and drum models**
- Extended Karplus–Strong (Jaffe & Smith 1983) adds to the K-S loop: a pick-direction lowpass, a pick-position comb filter, a string-damping filter (one or two poles/zeros, magnitude ≤ 1), a dynamic-level lowpass (bandwidth in Hz), a tuning allpass (fractional delay) and a string-stiffness allpass (inharmonicity) — [CCRMA PASP: Extended Karplus-Strong](https://ccrma.stanford.edu/~jos/pasp/Extended_Karplus_Strong_Algorithm.html)
- Commuted synthesis: because string and body are approximately LTI, the body's impulse response can be convolved with the pluck in advance and stored as the excitation table, replacing the expensive body filter; shorten long IRs by minimum-phase conversion or an exponential window; separate body outputs are lost — [CCRMA PASP: Commuted Synthesis](https://ccrma.stanford.edu/~jos/pasp/Commuted_Synthesis.html)
- Faust physmodels library: `ks` (1-D waveguide K-S), `guitar`/`nylonGuitar` ("doesn't currently implement a body"), `guitarBody` "not implemented yet", `modularInterpInstr` with a modal body (`modeInterpRes`) from impulse-response measurements of 3D-printed resonators; percussion: `djembe` (modal synthesis, modes "empirically calculated"), `marimba` (bar modes from `mesh2faust` + resonance tube), several bells (`mesh2faust`); exciters `strike`, `pluckString` — [faustlibraries physmodels](https://faustlibraries.grame.fr/libs/physmodels/)
- Karplus & Strong's 1983 paper was titled "Digital Synthesis of Plucked String and Drum Timbres"; loop length sets pitch (≈ fs/(N+½)), harder plucks carry more highs, muting = extra loss at note-off **[background]** — [Stanford, Ben Lynn: Karplus-Strong](https://theory.stanford.edu/~blynn/sound/karplusstrong.html)

### Inferences
- For the oud: one EKS string per course (pairs of strings with slight detune, i.e. two delay lines per course), fretless pitch via the tuning allpass plus continuous delay-length glides, the pick-position comb for plectrum (risha) position, and a measured or synthesised body IR applied by commuted synthesis (cheap) or by a `ConvolverNode` on the summed string output (more expensive but keeps body separate). This is an inference from the CCRMA material; no oud-specific browser or paper source was found.
- For the frame drum: a modal resonator bank (6–20 exponentially decaying sinusoids with empirically set frequencies/decays, as Faust's `djembe` does) excited by a short noise burst or `strike`; a membrane-hand damping parameter can be modelled as faster decay. Both instruments fit easily in one AudioWorklet in JS (Roma; stress tester) and could later be moved to Faust→WASM if voice counts grow.
- If plugin hosting is ever wanted, WAM 2.0 is the mature browser-native standard (iOS Safari included) and WebCLAP is the route to real desktop plugins (OB-Xf etc.) at the cost of a WASM/WASI host.

### Gaps
- No academic or engineering source on oud physical modelling (searches returned only general waveguide literature and a Colombian tiple thesis).
- No frame-drum-specific model; Faust's `djembe` is the closest sourced example.
- sfizz-webaudio's maintenance status and whether streaming SFZ is feasible in a browser were not verified; "sfizz-wasm" as named in the brief does not appear under that name.
- Per-instrument sizes for WebAudioFont presets and smplr's instrument sets were not found.

## Key question 4 — Real-time analysis in the browser: pitch, onset/tempo, chroma/key, LUFS, spectrograms

### Takeaway
Classical MIR runs comfortably in real time in the browser: essentia.js (Essentia C++ → WASM, ~2.5–3 MB) processes most features at 1.5–6.8 % of audio duration offline, with pYIN the outlier at up to 55 %; lightweight JS detectors (pitchy/McLeod, pitchfinder/YIN) and aubio-WASM cover tuner-grade pitch and tempo; BS.1770 LUFS exists as an AudioWorklet (`loudness-worklet`); neural models (CREPE, Basic Pitch) run via TensorFlow.js/ONNX but with second-scale latencies and mobile failures — keep them in Workers for offline analysis, not in the audio thread.

### Cited Findings
- essentia.js (Correya et al., TISMIR 2021): WASM back end compiled from Essentia C++; "as small as 2.5MB" (≈3 MB with add-ons); benchmarks on Chrome 89/Firefox 87 (Linux, macOS), Chrome 92/Firefox Nightly (Android), Chrome 87/Firefox 33 (iOS) on a 30 s clip: most algorithms 0.46–3.48 s (1.5–6.8 % of duration), MFCC 8.68 s (28.9 %) and pYIN 16.419 s (54.7 %) worst case; faster than Meyda except MFCC and HPCP; native Python Essentia fastest; real-time frame-wise extraction judged "possible for all the considered algorithms" even on Chrome for Android (the worst platform); TF.js models: inference 0.19–16.65 s (0.6–55.5 %), end-to-end 3.68–28.4 s (12.3–94.6 %), MusiCNN auto-tagging 62.18 s; VGGish failed on iOS and Chrome/Android; demos use AudioWorklet (ScriptProcessor deprecated and glitchy); WebGL results only on desktop — [TISMIR 10.5334/tismir.111](https://transactions.ismir.net/articles/10.5334/tismir.111)
- Meyda: JS feature extraction with offline and "real-time feature extraction using the Web Audio API"; MIT; WAC 2015 paper; ~1.7k stars — [meyda/meyda](https://github.com/meyda/meyda)
- pitchy: McLeod Pitch Method in plain JS for Node/browser, `findPitch` returns Hz plus a clarity score, fixed input length — [ianprime0509/pitchy](https://github.com/ianprime0509/pitchy); pitchfinder: YIN "adapted from aubio", plus McLeod, AMDF, etc.; maintainers call YIN "the best balance of accuracy and speed" but note it "occasionally provides values that are wildly incorrect", and McLeod "has been reported to perform better on lower frequencies" — [peterkhayes/pitchfinder](https://github.com/peterkhayes/pitchfinder)
- aubiojs: aubio compiled with Emscripten; `new Tempo(bufferSize, hopSize, sampleRate)`, `tempo.do(buffer)`, `getBpm()`; pitch detection also exposed; MIT; online demo — [qiuxiang/aubiojs](https://github.com/qiuxiang/aubiojs)
- CREPE: trained on 16 kHz audio (other rates resampled), 10 ms default hop, 360 pitch bins of 20 cents, capacities tiny/small/medium/large/full (smaller = faster, less accurate), MIT — [marl/crepe](https://github.com/marl/crepe); ONNX exports exist (`onnxcrepe`, `crepe-predictor` with five sizes) — [yqzhishen/onnxcrepe](https://www.github.com/yqzhishen/onnxcrepe), [crepe-predictor](https://pypi.org/project/crepe-predictor/); one browser tool lists CREPE ONNX models "from 1.9 MB (tiny) to 85 MB (full)" on ONNX Runtime Web with WebGPU while stating its models are "still being optimized" — unverified self-description — [jewelmusic music-transcription tool](https://jewelmusic-static.pages.dev/tools/music-transcription)
- Basic Pitch (TypeScript/TF.js, `@spotify/basic-pitch`): audio downmixed to mono and "resampled to 22050 Hz before processing"; `evaluateModel(audioBuffer, onFrames, onProgress)` → `outputToNotesPoly` → `addPitchBendsToNoteEvents` → `noteFramesToTime`; "works best on one instrument at a time"; long files should be windowed; Apache-2.0 (license text also mentions GPL — check) — [spotify/basic-pitch-ts](https://github.com/spotify/basic-pitch-ts); community reports that the official browser demo has been stuck "Loading file..." for many users and that dense mixes transcribe poorly — anecdotal — [Product Hunt post](https://www.producthunt.com/posts/1238029)
- LUFS: `loudness-worklet` — ITU-R BS.1770-5 `AudioWorkletProcessor`, zero dependencies, momentary/short-term/integrated, max values and loudness range, verified against the ITU-R BS.2217 test suite, file measurement via `OfflineAudioContext` — [loudness-worklet (socket.dev listing)](https://socket.dev/npm/package/loudness-worklet); `needles` — EBU R128/BS.1770-4 meter on the deprecated `ScriptProcessorNode`, true-peak and LRA listed as future work — [domchristie/needles](https://github.com/domchristie/needles); LUFSly — framework-free pure-JS BS.1770-4 app with true peak and dynamic range (reference implementation) — [Macusercom/lufsly](https://github.com/Macusercom/lufsly); AudioMass ships a `lufs.js` module — [pkalogiros/AudioMass](https://github.com/pkalogiros/AudioMass)
- Spectrogram: `AnalyserNode.fftSize` must be a power of two from 32 to 32768 (default 2048); `frequencyBinCount = fftSize/2` — [MDN AnalyserNode.fftSize](https://developer.mozilla.org/en-US/docs/Web/API/AnalyserNode/fftSize)
- Where to run analysis: Firefox's guidance is that batch work spanning much more than one 128-frame block should be split across blocks or moved to a Web Worker — [Mozilla Hacks 2020](https://hacks.mozilla.org/2020/05/high-performance-web-audio-with-audioworklet-in-firefox/); openDAW runs analysis, BPM detection and ONNX inference in Workers and streams meters/spectra from the audio thread lock-free — [openDAW introduction.md](https://raw.githubusercontent.com/andremichelle/opendaw/main/introduction.md); `ringbuf.js` (padenot) is the standard wait-free SPSC ring buffer over SharedArrayBuffer for audio queues and parameter/event passing between Worker/main thread and AudioWorklet; needs COOP/COEP; MPL-2.0; Firefox, Chrome(+Android) and Safari supported as of 2023-05-25 — [padenot/ringbuf.js](https://github.com/padenot/ringbuf.js)
- Amped Studio's "Hum and Beatz" turns humming/beatboxing into MIDI notes and beats (no accuracy figures) — [KVR 2018](https://www.kvraudio.com/news-print.php?id=43058)

### Inferences
- A tuner/pitch display for the oud (fretless, needs cents) is best served by McLeod/YIN at 1024–2048-sample frames in an AudioWorklet or Worker (sub-10 ms compute), with CREPE/pYIN reserved for offline transcription in a Worker (pYIN at ~55 % of real time in essentia.js is still real-time capable but leaves no headroom on mobile).
- Key/chroma (HPCP) and onset/tempo are available in essentia.js and aubiojs; HPCP is one of the two features where Meyda beat essentia.js, so compare both if chroma is the main need.
- Loudness normalisation of exports (e.g. −16 LUFS as already used in the project's listening study) can be done in-browser with `loudness-worklet` on an `OfflineAudioContext` pass.

### Gaps
- No published browser benchmark of CREPE on ONNX Runtime Web / WebGPU; the only figure is model size (1.9–85 MB) from an unverified tool page.
- No measured browser speed or accuracy for Basic Pitch TS.
- No AudioWorklet-specific benchmark for essentia.js (its paper measured offline chains).
- The browser-side claims of `loudness-worklet` (BS.2217 compliance) come from its package listing and were not independently verified.

## Key question 5 — Existing browser DAWs and editors: what their architectures teach

### Takeaway
Every serious browser DAW that documents its engine has converged on: a single engine running in an AudioWorklet (openDAW: Rust→WASM; Audiotool: Rust, with a native "Booster" fallback; Amped: WASM + WAM plugins), workers for file I/O and analysis, OPFS/IndexedDB or cloud for persistence, and a transactional data model mirrored to the audio thread (openDAW boxes; Signal's transactions). The commercial players' public engineering material is thin; the usable open references are openDAW (AGPL/commercial), Signal + wavelet (MIT), Strudel (Codeberg), Elementary and Glicol.

### Cited Findings
- **openDAW** (André Michelle, © 2025): AGPL v3+ with a commercial dual licence; TypeScript, Rust, Sass, JS for scripted devices; Node ≥ 23; monorepo (Lerna/Turborepo, `packages/`, `crates/`); 34 stock devices incl. scripted Apparat (instrument), Spielwerk (MIDI effect), Werkstatt (audio effect); WebCLAP hosting; runtime libraries jszip, soundfont2, zod, ffmpeg.wasm, markdown-it, d3-force; "tries to avoid external libraries and frameworks"; cloud backups, Live Rooms; 4,843 commits, 2.4k stars, 231 forks; dev server over HTTPS (mkcert) on :8080 — [andremichelle/opendaw](https://github.com/andremichelle/opendaw); architecture: layered TS where "Each layer may only depend on the layers above it"; boxes are "typed records with addressable fields" and "a dumb record", adapters add behaviour; every edit is a transaction with undo and `sync-source/sync-target` mirroring across threads or peers; collaboration on yjs over websocket (`ysync/`, `sync-log/`); `studio-p2p` exchanges assets over WebRTC data channels in chunks; OPFS via a `lib-fusion` worker; `project/` handles bundles, migration, validation, recovery; `lib-dawproject` reads and writes DAWproject; `lib-midi` decodes SMF, `studio-core` imports/exports MIDI; WAV encoding in `lib-dsp`; ffmpeg via an `@ffmpeg/ffmpeg` peer dependency; cloud connectors for Dropbox/Nextcloud; `studio-core/capture/` for audio and MIDI recording — [openDAW introduction.md](https://raw.githubusercontent.com/andremichelle/opendaw/main/introduction.md); a 2026-08-22 review notes projects live in browser-owned storage so clearing browser data deletes them, and that custom DSP is possible through Werkstatt/Spielwerk — [Bedroom Producers Blog review](https://bedroomproducersblog.com/2026/08/22/opendaw-review/)

- **Wavacity**: Audacity 3.0.0 compiled to WebAssembly by Adam Hilss, reusing his 2022 wxWidgets and PortAudio WASM ports; GPL v2; works on phones but "the interface isn't built for touch" — [Hackaday 2023-10-05](https://hackaday.com/2023/10/05/audacity-runs-surprisingly-well-in-your-browser), [Korben](https://korben.info/en/wavacity-audacity-in-your-web-browser.html)
- **AudioMass**: JavaScript editor built by concatenating modules (`engine.js`, `recorder.js`, `multitrack.js`, `fx-*.js`, `lufs.js`) with wavesurfer.js, lzma.js and id3.js; multitrack mode with clip dragging, crossfades on overlaps, recording to armed channels and bounce; ~3.0k stars — [pkalogiros/AudioMass](https://github.com/pkalogiros/AudioMass)
- **Other open engines**: glissando-daw/web-synth is "a web-based DAW written in Rust/WebAssembly and TypeScript" whose `AudioWorkletProcessor` runs WASM DSP — search snippet — [glissando-daw/web-synth](https://github.com/glissando-daw/web-synth)
- **WAC 2025** (IRCAM, Paris, 19–21 Nov 2025, 10th anniversary) DAW-relevant papers: RhizomeBridge (VST/AU ↔ Node.js bridge "with sample-accurate precision"), DawBi (WebSocket DAW ↔ AI assistant), "Disk Streaming Audio in the Browser" (Brian Francis Bishop, SoundEtch.org; "streaming audio to and from disk storage" keeps memory and start delay low; addresses "storage quotas, cross-thread communication, and dropouts"; its reference list points to the Web Audio 1.1 spec, the COOP/COEP guide, ringbuf-js, the File System API, OPFS Explorer and a priority-inversion Chromium issue), WCLAP — [WAC 2025 programme](https://medias.ircam.fr/en/event/web-audio-conference-2025-2025), [Zenodo 17642128](https://zenodo.org/records/17642128)
- The DAW market signal: PreSonus/Bitwig/Steinberg adopted DAWproject (see Q6), openDAW implements it in TypeScript — relevant for interchange with desktop users.

### Inferences
- The architecture that recurs — engine in one worklet, immutable/transactional project model mirrored to the audio thread, workers for I/O and analysis, OPFS for audio — is the one to adopt; the existing project's Web Audio + AudioWorklet recording + IndexedDB setup already matches the first tier, and the missing pieces are a transactional project model with undo, an engine-side transport and OPFS for audio blobs.
- Audiotool's Booster and Soundtrap's Mac app show that even well-funded browser DAWs keep a native escape hatch for latency and CPU; a Somali-music studio aimed at phones and laptops should budget for mobile CPU limits (see Q7) rather than assume desktop headroom.
- Signal's experience (MobX → Jotai, leaf-focused re-rendering) is the most directly transferable React lesson: keep high-churn transport/meter state out of React props.

- Mod Audio (MOD Devices' web UI) was not researched.
- Ableton Learning Music's technology is undocumented on its site.

## Key question 6 — Persistence and formats: OPFS vs IndexedDB, quotas, export encoders, MIDI/MusicXML, DAWproject, Ableton Link

### Takeaway
Use OPFS (from a Worker, `FileSystemSyncAccessHandle`) for audio blobs and keep IndexedDB for project metadata; both share one per-origin quota (Chromium 60 % of disk, Firefox min(10 % disk, 10 GiB) best-effort, Safari ~60 % in browser apps / ~15 % in embedded WebViews, with Safari evicting script-created data after 7 days without interaction). Export WAV by hand, MP3 via LAME-WASM (~66 KiB), FLAC via libFLAC-WASM (no browser encodes FLAC natively), Opus/AAC via WebCodecs `AudioEncoder` (Chrome 94, Firefox 130, Safari 26). MIDI via `@tonejs/midi`, MusicXML via Verovio (already in the project), DAWproject (ZIP + XML, MIT, supported by Bitwig/Studio One/Cubase/Cubasis/n-Track and implemented in TS by openDAW) for interchange; Ableton Link has no browser target.

### Cited Findings
- Storage quotas (MDN): Chromium "an origin can store up to 60% of the total disk size" (600 GiB on a 1 TiB drive), browser-wide cap 80 %; Firefox best-effort = smaller of 10 % of disk or the 10 GiB group limit, persistent up to 50 % of disk capped at 8 TiB; Safari/WebKit on macOS 14/iOS 17+: "around 60% of total disk" per origin in browser apps, "around 15%" in embedded WebViews (Home Screen web apps get the browser quota), cross-origin frames ~1/10 of parent, caps 80 %/20 %; earlier Safari: 1 GiB initial then a user prompt; eviction is LRU under storage pressure, all-or-nothing per origin, skips persistent origins; Safari "proactively evicts data when cross-site tracking prevention is turned on. If an origin has no user interaction … in the last seven days of browser use, its data created from script will be deleted"; `navigator.storage.persist()` prompts in Firefox and is auto-decided in Chromium/Safari; `localStorage`+`sessionStorage` capped at 10 MiB total; IndexedDB, Cache and OPFS are all governed by one storage manager — [MDN Storage quotas and eviction criteria](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
- OPFS: Chrome 86, Edge 86, Firefox 111, Safari 15.2; "The entry point to the fastest possible file operations is a FileSystemSyncAccessHandle" with synchronous `read/write/truncate/flush/close` in Workers; "highly optimized for performance"; same quota as IndexedDB; deleted when site data is cleared; no permission prompts; used as a SQLite-WASM backend — [web.dev: The origin private file system](https://web.dev/articles/origin-private-file-system); OPFS "runs in a worker, keeping your app responsive" — [Patrick Brosset, 2023-01-17](https://patrickbrosset.com/articles/2023-01-17-web-storage/)
- openDAW stores files in OPFS through a worker, bundles projects with jszip, converts audio with `@ffmpeg/ffmpeg`, encodes WAV itself, and syncs to Dropbox/Nextcloud — [openDAW introduction.md](https://raw.githubusercontent.com/andremichelle/opendaw/main/introduction.md)
- Decoded-audio memory hazards: `decodeAudioData` on large MP3s crashed Chrome tabs (>~8 MB in a 2013 issue; a 68 MB file loaded in Safari but crashed Chrome) **[background]** — [wavesurfer.js issue #9](https://github.com/katspaugh/wavesurfer.js/issues/9); a 70.9 MB file decoded to "almost 10 GB" of memory (2019 blog) — [jessuni](https://jessuni.typlog.io/2019/why-generating-waveform-for-a-large-audio-file-may-not-be-a-good-thing); WebKit keeps decoded buffers alive ~1 minute after references drop — [WebKit bug 189337](https://bugs.webkit.org/show_bug.cgi?id=189337); iOS Safari crashed after ~10 decode iterations, `arrayBuffer.slice(0)` workaround — [WebKit bug 230192](https://bugs.webkit.org/show_bug.cgi?id=230192); 64-bit Chrome tab crash near 4 GB — [Stack Overflow mirror](https://kaweah.freedombox.rocks/kiwix/content/stackoverflow.com_en_all_2023-11/questions/54943968/64-bit-chrome-and-edge-browser-tab-crashes-when-trying-to-use-more-than-4gb-of)
- Encoders: `wasm-media-encoders` compiles LAME (MP3) and Ogg Vorbis to WASM, MP3 build "about 66 KiB combined and gzipped", no FLAC/WAV — [wasm-media-encoders on npm](https://www.npmjs.com/package/wasm-media-encoders); `lamejs` (pure JS LAME port) claims ~20× real time ("132-second sample in about 6.5 seconds") in Node and Chrome, 903 stars, 42 open issues, no releases listed — [zhuker/lamejs](https://github.com/zhuker/lamejs); `libflacjs` packages libFLAC for the browser with a WebWorker setup — [libflacjs on npm](https://npmjs.com/package/libflacjs); `@mediabunny/flac-encoder` is a "size-optimized WASM build of libFLAC" and states "No browser currently supports FLAC encoding in their WebCodecs implementations"; check `canEncodeAudio('flac')` then `registerFlacEncoder()` — [mediabunny FLAC encoder](https://mediabunny.dev/guide/extensions/flac-encoder); `wasm-audio-decoders` (decode only; FLAC decoder ~65 KiB) — [eshaz/wasm-audio-decoders](https://github.com/eshaz/wasm-audio-decoders); ffmpeg.wasm is MIT and "experimental" — [ffmpegwasm/ffmpeg.wasm](https://github.com/ffmpegwasm/ffmpeg.wasm); third-party guides put `@ffmpeg/core` and `core-mt` at ~30–31 MB each and note core-mt needs SharedArrayBuffer (COOP/COEP) — [Shotstack guide](https://shotstack.io/learn/ffmpeg-wasm/), [DEV Community](https://dev.to/ali_salame/how-i-built-a-browser-based-video-converter-with-ffmpeg-webassembly-no-server-required-1bl8)
- WebCodecs `AudioEncoder`: Chrome 94, Firefox 130, Safari 26 (iOS mirrors); Opus codec Chrome 110 / Firefox 130 / Safari 26; `bitrateMode` Chrome 119 / Firefox 130 / Safari 26 — [mdn/browser-compat-data AudioEncoder.json](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/AudioEncoder.json); secure contexts and dedicated Workers; `isConfigSupported()`; "Limited availability" — [MDN AudioEncoder](https://developer.mozilla.org/en-US/docs/Web/API/AudioEncoder)
- MIDI: `@tonejs/midi` parses SMF to JSON (header tempos/time signatures/PPQ; tracks with instrument, notes in seconds and ticks, named control changes) and encodes back via `toArray()`; depends on `midi-file`; MIT; ~1.0k stars — [Tonejs/Midi](https://github.com/Tonejs/Midi); openDAW `lib-midi` decodes SMF and `studio-core` imports/exports MIDI — [openDAW introduction.md](https://raw.githubusercontent.com/andremichelle/opendaw/main/introduction.md)
- MusicXML/engraving: Verovio is a C++20 engraving library (MEI native, converters for MusicXML, Humdrum, ABC, PAE, Musedata, EsAC; SVG output; Standard MIDI file export via the embedded MidiFile library) with a JavaScript toolkit on npm; LGPL-3.0; 969 stars — [rism-digital/verovio](https://github.com/rism-digital/verovio)
- DAWproject: a ZIP with `.dawproject` extension containing UTF-8 `project.xml` and `metadata.xml` (schemas `Project.xsd`, `MetaData.xsd`); stores audio/note/automation timelines, note expression, embedded plug-in states, tempo and time signature, track/channel structure, warps; v1.0 "stable"; MIT; supported by Bitwig Studio 5.0.9, PreSonus Studio One 6.5, Steinberg Cubase 14, Cubasis 3.7.1, VST Live 2.2, n-Track Studio 10.2.2; converters DawVert and git-moss ProjectConverter (Reaper); no JS implementation listed — [bitwig/dawproject](https://github.com/bitwig/dawproject); announced September 2023 — [Bitwig story](https://www.bitwig.com/stories/bitwig-and-presonus-are-making-it-easy-to-share-projects-between-programs-271/); openDAW's `lib-dawproject` "reads and writes the DAWproject interchange format" in TypeScript — [openDAW introduction.md](https://raw.githubusercontent.com/andremichelle/opendaw/main/introduction.md)
- Ableton Link: devices "discover each other automatically" on a local network; platforms Windows (MSVC 2022), macOS (Xcode 16.2), Linux (Clang 13/GCC 10); iOS via LinkKit; no browser, WASM or JS target mentioned; GPLv2+ or proprietary licence — [Ableton/link](https://github.com/Ableton/link); `ableton-link-rs` is an early-stage GPLv3 Rust reimplementation, not a browser build — [docs.rs ableton-link-rs](https://docs.rs/crate/ableton-link-rs/latest)

### Inferences
- Memory arithmetic (computed, not sourced): 32-bit float stereo at 48 kHz is 384 KB/s ≈ 23 MB per minute ≈ 1.4 GB per hour of decoded audio; a 10-track, 5-minute session fully decoded is ≈1.2 GB, which is why openDAW and the WAC 2025 paper stream from disk (OPFS) and why WebKit's and Chrome's decode crashes matter. Keep decoded audio per track in OPFS-backed chunks and decode on demand in a Worker.
- Because browsers have no UDP/multicast sockets and Link's README lists no web target, Link sync from a browser is only possible through a native bridge (desktop helper relaying beat/tempo over WebSocket/WebRTC), the same pattern Audiotool's Booster and Soundtrap's desktop app use for other reasons.
- For exports: WAV always; MP3 via `wasm-media-encoders` (small, WASM); FLAC via mediabunny/libflacjs; Opus/AAC via WebCodecs where `isConfigSupported` passes. Avoid ffmpeg.wasm for a client bundle unless broad import (video/ALAC/legacy) is needed — ~30 MB and COOP/COEP for the threaded build.
- Safari's 7-day eviction rule means a user who records on iPhone and returns two weeks later may have lost unsynced audio: request `persist()`, surface a "back up" prompt, and sync to R2 (the platform's existing presigned-URL path) early.

### Gaps
- No direct OPFS-vs-IndexedDB throughput benchmark for audio-sized blobs was found; the WAC 2025 disk-streaming paper likely holds one but its PDF text was not extractable.
- Official byte sizes for `@ffmpeg/core` / `core-mt` were not found in primary docs.
- Whether any JS/TS DAWproject library other than openDAW's `lib-dawproject` exists was not established.

## Key question 7 — Known limits and failure modes, with mitigations

### Takeaway
The failure modes are well catalogued: suspended contexts until a gesture, main-thread timer throttling in background tabs, the historic 6-context-per-process cap in Chrome, decoded-audio memory blow-ups, iOS route/sample-rate and PWA-background silences, Safari capture/worklet bugs still open in 2026, and the COOP/COEP tax that SharedArrayBuffer imposes on third-party embeds. Mitigations are equally standard: one context per app, resume on gesture, Worker-hosted scheduler timer, `audioSession.type = "playback"`, stream audio from OPFS, avoid SAB unless cross-origin isolation is acceptable, and test on low-end phones because mobile Chrome is the slowest platform in the only mobile benchmark found.

### Cited Findings
- AudioContext count: Chrome threw "The number of hardware contexts provided (6) is greater than or equal to the maximum bound (6)"; the limit is shared across tabs in one process, often same-domain; `close()` frees a slot; Chromium's Chris Wilson advised "one per app" (2014); still reported in 2017; no source confirms removal — **[background]** — [W3C public-audio list, Wilson 2014](https://lists.w3.org/Archives/Public/public-audio/2014JulSep/0137.html), [JotForm thread 2017](https://www.jotform.com/answers/1073050), [Stack Overflow mirror](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/25977269/using-audiocontext-in-multiple-iframes)
- Autoplay/suspension: see Q2 — [Chrome Developers: Autoplay](https://developer.chrome.com/blog/autoplay), [MDN Autoplay guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)
- Background throttling: see Q1 — [Chrome 88 timer throttling](https://developer.chrome.com/blog/timer-throttling-in-chrome-88), [Chrome 57 background tabs](https://developer.chrome.com/blog/background_tabs)
- Cross-origin isolation: `SharedArrayBuffer` is "Required for WebAssembly threads" and needs `Cross-Origin-Embedder-Policy: require-corp` + `Cross-Origin-Opener-Policy: same-origin` (Chrome ≥ 92 desktop); COEP blocks cross-origin scripts, styles, images and iframes that lack CORP/CORS; iframes need their own CORP and `allow="cross-origin-isolated"`; COOP severs `window.opener`/popup communication; `document.domain` becomes immutable; `credentialless` COEP (Chrome 96+/Edge) relaxes CORP for resources; use `Cross-Origin-Embedder-Policy-Report-Only` first and check `self.crossOriginIsolated`; high-res timers improve from 100 µs to 5 µs — [web.dev: COOP and COEP](https://web.dev/articles/coop-coep); ringbuf.js and the threaded ffmpeg.wasm both require these headers — [padenot/ringbuf.js](https://github.com/padenot/ringbuf.js), [Shotstack ffmpeg.wasm guide](https://shotstack.io/learn/ffmpeg-wasm/)
- AudioWorklet scope limits: no Fetch API in the worklet scope (assets must be fetched elsewhere and transferred); Firefox lagged on ES-module `import` inside worklet scripts — vendor post — [superpowered.com](https://superpowered.com/riding-the-latest-waves-on-the-web); Roma also notes Embind's ES6 module import "is still not supported in Firefox" (2022) and suggests concatenating the Emscripten glue into the processor script — [Zenodo 6767468](https://zenodo.org/records/6767468); WebKit has an open request to expose `performance.now()` in `AudioWorkletGlobalScope` (2026-10-13) — [WebKit bug 326586](https://bugs.webkit.org/show_bug.cgi?id=326586)
- Open WebKit Web Audio bugs relevant to a DAW (all NEW/REOPENED as of the 2026 list): 326286 iOS 26.2–27 crackle with echo-cancelled capture (2026-10-21); 255949 "Loud crackling and pops in AudioContext during user actions" on iPad Pro/M1 (2026-10-19); 328316 `MediaElementAudioSourceNode` replays the file start for ~1 s after seek/resume (2026-10-30); 303421 iOS crash in an AudioWorklet out-of-memory test (2025-12-05); 296976/290767 denormals tests failing (2025); 258864 Bluetooth route distortion (2024-07-26); 253952 20 ms capture buffer (2023); 251350 worklet PCM sample-count mismatch (2023); 244203 corrupted AudioWorklet recordings (2023); 226240 AudioWorklet glitches (2023) — [WebKit AudioWorklet bug list](https://bugs.webkit.org/buglist.cgi?quicksearch=AudioWorklet&order=changeddate%20DESC)
- Memory: wasm32 is capped at 4 GB; iPhone Safari tabs reportedly die near ~350 MB (vendor anecdote) — [superpowered.com](https://superpowered.com/riding-the-latest-waves-on-the-web); decode-related crashes and leaks — see Q6
- Mobile CPU: in essentia.js's benchmarks "Chrome on Android had the worst Essentia.js performance, followed by Firefox on Android", several TF.js models failed outright on iOS and Chrome/Android — [TISMIR 10.5334/tismir.111](https://transactions.ismir.net/articles/10.5334/tismir.111); Roma cautions that on "mobile phones … the differences between WebAssembly and JavaScript become less relevant" — [Zenodo 6767468](https://zenodo.org/records/6767468); Audiotool tests its engine on "lower-tier Chromebooks" — [Audiotool board](https://audiotool.com/board/news/join_the_audio_engine)
- Firefox: Web Audio autoplay blocked until sticky activation by default — [MDN Autoplay guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay); SharedArrayBuffer in non-isolated pages only in Nightly behind a flag — [karplus-stress-tester](https://github.com/jackschaedler/karplus-stress-tester)
- Storage eviction (Safari 7-day rule, LRU all-or-nothing) — see Q6 — [MDN Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

### Inferences
- For a Next.js app on Vercel that also loads Stripe and other third-party scripts/iframes, turning on COOP/COEP (needed for SharedArrayBuffer/ringbuf.js/threaded WASM) is a site-wide decision with real breakage risk; the pragmatic path is to keep the DAW on `MessagePort` with transferred `ArrayBuffer`s (Firefox's guidance) and only enable isolation on a dedicated `/studio` route or sub-origin after a Report-Only trial. Whether Stripe's iframes carry CORP headers was not checked here.
- A single long-lived `AudioContext` created on load and `resume()`d on the first click, with all instruments, recording and metering as nodes on it, sidesteps the context cap, autoplay rules and the iOS "silent after background" class of bugs (re-check `state` on `visibilitychange` and re-resume on the next gesture).
- Because iOS output sample rate changes with the route (speaker 48 kHz vs Bluetooth 44.1 kHz) and Web Audio contexts do not follow, the engine should treat `context.sampleRate` as mutable across sessions: resample stored clips on load rather than assuming a project rate, and recreate the context when a route change is detected.
- Budget for low-end Android: keep per-block work well under the ~2.7 ms budget at 48 kHz with headroom for the browser's own nodes, prefer one worklet, avoid per-block allocations (openDAW's "zero allocations per render quantum"), and defer analysis to Workers.

### Gaps
- No confirmation that the 6-AudioContext limit still exists in current Chrome; treat "one context per app" as a design rule rather than a measured constraint.
- No independent source for the ~350 MB iOS tab memory ceiling.
- No measurement of AudioWorklet CPU headroom on representative 2025–2026 Android phones.
- Whether AudioWorklet processing itself is ever throttled in background tabs (vs the main-thread scheduler timer) is not documented in the sources found.
- Strudel author Felix Roos's "Web Audio Scheduling" article now redirects from `loophole-letters.vercel.app` to an unrelated domain and was not read.
