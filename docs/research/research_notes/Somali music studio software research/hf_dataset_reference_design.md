# Publishing a citable, reference-grade music/MIR dataset on Hugging Face (2025–2026) — mechanics and design

Scope note: these notes cover (1) current Hub mechanics, (2) dataset-card best practice, (3) licensing, (4) what made reference MIR datasets reference-grade (incl. culturally specific corpora), (5) benchmark design conventions, (6) glossary/lexicon datasets and Somali language metadata. The target dataset holds ONLY rights-clean material (AI-model outputs with prompts/seeds/adapter names/metrics, a synthetic benchmark with ground-truth notes, symbolic data, evaluation records, a Somali–English glossary, documentation) and must be honest that no archival recordings are included. Research date: 2026-11-07. The web-search budget ran out part-way; the remaining items were fetched directly from primary pages. Items I could not reach are listed under Gaps rather than guessed.

---

## Key Question 1 — Hugging Face Hub mechanics: repo layout, card YAML, formats, audio, viewer, upload APIs, storage, gating, visibility, DOI, Croissant, versioning, citation, loading

### Takeaway
A dataset repo is a Git repo whose `README.md` YAML header both documents the dataset and configures it (`configs` → `data_files`/`data_dir` per subset and split; `dataset_info` → feature types). For 30-second MP3/WAV clips the documented recommendation is raw audio files plus a `metadata.jsonl` (`file_name` column) rather than audio-in-Parquet (which is advised only for files under about 1 MB); tabular records (evaluations, glossary, notes) should be Parquet or JSONL. Loading scripts are gone (`datasets` 4.0 removed them), the Data Studio viewer is on by default for public repos and auto-converts the first 5 GB to Parquet, `upload_folder`/`hf upload` stream and resume via Xet, DOIs are minted per revision through DataCite and lock delete/rename/visibility, and Croissant JSON-LD is generated automatically from the Parquet conversion plus card metadata.

### Cited Findings

Repository layout and formats
- Natively supported file formats: Parquet, CSV/TSV, JSON/JSONL, Arrow, text, images, audio (`.wav`, `.mp3`, …), video, PDF, WebDataset `.tar`, Lance; compressed ZIP/GZIP/ZSTD/BZ2/LZ4/LZMA also supported — [HF Hub: Uploading datasets](https://huggingface.co/docs/hub/datasets-adding)
- "For most types of datasets, Parquet is the recommended format … CSV or JSON Lines/JSON can be used for tabular data (prefer JSON Lines for nested data)"; "For image and audio datasets, uploading raw files is the most practical for most use cases since it's easy to access individual files"; Parquet is recommended "for more general use cases involving analytics, data filtering or metadata parsing" at large scale — [HF Hub: Uploading datasets](https://huggingface.co/docs/hub/datasets-adding)
- "Other formats and structures may not be recognized by the Hub" (i.e., MusicXML/MIDI/PDF scores will be hosted and downloadable but will not become viewer columns) — [HF Hub: Uploading datasets](https://huggingface.co/docs/hub/datasets-adding)
- Simplest repo: `README.md` + one data file; splits are inferred from file names containing `train`/`test`/`validation` delimited by non-word characters (underscore, dash, space, dot, digits), or from directories named after the split. Equivalent keywords: `train, training`; `validation, valid, val, dev`; `test, testing, eval, evaluation`. Custom split names use `data/<split_name>-xxxxx-of-xxxxx.ext` — [HF Hub: File names and splits](https://huggingface.co/docs/hub/datasets-file-names-and-splits)
- Text-file caveat for UI uploads: "Text file extensions are not tracked by Git LFS by default, and if they're greater than 10MB, they will not be committed and uploaded" — compress large CSV/JSONL or convert to Parquet — [datasets: Share a dataset to the Hub](https://huggingface.co/docs/datasets/upload_dataset)

Dataset card YAML header (exact field names)
- Card = `README.md`; YAML between `---` lines; metadata enables filtering/discovery and licence display; "To see metadata fields, see the detailed Dataset Card specifications" at `hub-docs/datasetcard.md` — [HF Hub: Dataset Cards](https://huggingface.co/docs/hub/datasets-cards)
- The spec's fields and types: `license` (string; identifier from the licences page), `license_name`/`license_link` (used with `license: other`; link may be `LICENSE`, `LICENSE.md` or a URL), `license_details` (legacy), `language` (list), `language_details` (BCP-47 e.g. `fr-FR`), `tags` (list), `annotations_creators` (`crowdsourced`, `found`, `expert-generated`, `machine-generated`), `language_creators`, `pretty_name`, `size_categories` (list), `source_datasets`, `task_categories`, `task_ids`, `paperswithcode_id`, `configs` (list of `config_name` + `data_files` [`split`,`path`]), `dataset_info` (`features` [`name`,`dtype`], `config_name`, `splits` [`name`,`num_bytes`,`num_examples`], `download_size`, `dataset_size`; may be a list for several configs), `extra_gated_fields`, `extra_gated_prompt` — [hub-docs/datasetcard.md](https://github.com/huggingface/hub-docs/blob/main/datasetcard.md?plain=1)
- Allowed `size_categories` strings: `unknown`, `n<1K`, `1K<n<10K`, `10K<n<100K`, `100K<n<1M`, `1M<n<10M`, `10M<n<100M`, `100M<n<1B`, `1B<n<10B`, `10B<n<100B`, `100B<n<1T`, `n>1T` — [datasets size_categories.json](https://raw.githubusercontent.com/huggingface/datasets/main/src/datasets/utils/resources/size_categories.json)
- `language` "must be an ISO 639-1, 639-2 or 639-3 code (two/three letters), or a special value like 'code', 'multilingual'"; `annotations_creators` options `found, crowdsourced, expert-generated, machine-generated, no-annotation, other`; `multilinguality` options `monolingual, multilingual, translation, other`; `source_datasets` options `original`, `extended`; `license` may be `str | list[str]` — [huggingface_hub DatasetCardData](https://huggingface.co/docs/huggingface_hub/package_reference/cards)
- The card page itself says `language` is a "List of ISO 639-1 code for your language" — [HF Hub: Dataset Cards](https://huggingface.co/docs/hub/datasets-cards). Both styles are in use: `tufaax/en-so-parallel-clean-8k` declares `language: [en, so]` — [tufaax README](https://huggingface.co/datasets/tufaax/en-so-parallel-clean-8k/raw/main/README.md); `google/fleurs` declares Somali as `- som` (ISO 639-3) with a `lang_id` label `so_so` — [google/fleurs README](https://huggingface.co/datasets/google/fleurs/raw/main/README.md)
- Force a modality with a tag (`audio`, `text`, `tabular`, …); associate a library with tags such as `datasets`, `mlcroissant`, `pandas`, `webdataset`; linking a paper URL auto-adds an `arxiv:<ID>` tag — [HF Hub: Dataset Cards](https://huggingface.co/docs/hub/datasets-cards)
- Programmatic card creation: `DatasetCardData(language=…, license=…, annotations_creators=…, task_categories=[…], task_ids=[…], multilinguality=…, pretty_name=…, size_categories=…, source_datasets=…, config_names=…)`; `DatasetCard.from_template(card_data, template_path=None, **kwargs)`; `card.push_to_hub(repo_id, repo_type="dataset")`; `metadata_update(repo_id, metadata, repo_type="dataset", overwrite=False)`; `card.validate(repo_type="dataset")` runs the Hub's validation — [huggingface_hub cards reference](https://huggingface.co/docs/huggingface_hub/package_reference/cards)

Manual configuration (`configs`)
- `configs:` list; "`config_name` field is required even if you have a single subset"; `data_files` may be a string, a list, or `[{split: train, path: "data.csv"}, {split: test, path: "holdout.csv"}]`; paths accept globs (`"data/*.csv"`); multiple subsets = several `config_name` entries; `default: true` picks "which subset the Dataset Viewer shows first, and which subset data libraries load by default"; subsets are listed default first then alphabetical; `data_dir: "main"` resolves files relative to a directory and auto-assigns splits from file names; `data_dir` + `data_files` can be combined; builder params (e.g. `sep: "\t"`) can be set per config — [HF Hub: Manual Configuration](https://huggingface.co/docs/hub/datasets-manual-configuration)
- Viewer-side YAML example for a single config with train/test files and glob/list paths — [HF Hub: Data Studio](https://huggingface.co/docs/hub/datasets-viewer)

Audio: AudioFolder vs Parquet
- Audio files may sit at the repo root or in a subdirectory; "Multiple formats are supported at the same time, including AIFF, FLAC, MP3, OGG and WAV"; splits via `train/`, `test/` directories — [HF Hub: Audio Dataset](https://huggingface.co/docs/hub/datasets-audio)
- Extra columns come from `metadata.csv`, `metadata.jsonl` or `metadata.parquet`; the file "must have a `file_name` column"; the metadata file must be "in the same directory with the audio files it is linked to, or in any parent directory", and then `file_name` is "a full relative path to the audio files"; "Metadata files cannot be put in subdirectories of a directory with the audio files"; "any column named `file_name` or `*_file_name` should contain the full relative path" — [HF Hub: Audio Dataset](https://huggingface.co/docs/hub/datasets-audio)
- Several audio files per row: name columns `input_file_name`, `output_file_name`, etc.; lists of audio: `file_names` or `*_file_names` — [datasets: Create an audio dataset](https://huggingface.co/docs/datasets/audio_dataset)
- Directory names become a `label` column unless `drop_labels: true` is set in the config — [HF Hub: Audio Dataset](https://huggingface.co/docs/hub/datasets-audio)
- Audio in Parquet: columns must be a struct with binary `bytes` and string `path`; declare `dataset_info: features: - name: audio dtype: audio`; "Parquet is recommended for small audio files (<1MB per audio file) and small row groups (100 rows per row group, which is what `datasets` uses for audio). For larger audio files it is recommended to use the WebDataset format, or to share the original audio files (optionally with metadata files)" — [HF Hub: Audio Dataset](https://huggingface.co/docs/hub/datasets-audio)
- `push_to_hub()` writes `README.md` + `data/train-00000-of-00001.parquet`; `Dataset.from_dict({"audio": [paths]}).cast_column("audio", Audio())` then `push_to_hub("user/my_dataset")`; `private=True` works only on first creation — [datasets: Create an audio dataset](https://huggingface.co/docs/datasets/audio_dataset), [datasets: Share a dataset](https://huggingface.co/docs/datasets/upload_dataset)
- `datasets` ≥ 4.0: "torchcodec replaces soundfile for audio decoding" (torch ≥ 2.7, FFmpeg ≥ 4; "Not available for Windows yet"), samples come back as `AudioDecoder` objects (old `array`/`sampling_rate` access still supported), `Sequence` replaced by a `List` type — [datasets 4.0.0 release](https://github.com/huggingface/datasets/releases/tag/4.0.0). `dataset.decode(False)` returns path/bytes instead of decoded audio; `decode(num_threads=…)` speeds up streaming; `filters=[("label","=",0)]` works best with Parquet metadata — [datasets: Load audio data](https://huggingface.co/docs/datasets/audio_load)

Loading scripts
- `datasets` 4.0.0 release notes: "Remove scripts altogether" and "`trust_remote_code` is no longer supported" (release shown as 09 Jul; the page does not display the year) — [datasets 4.0.0 release](https://github.com/huggingface/datasets/releases/tag/4.0.0)
- Hub policy for large datasets: "Avoid the use of custom loading scripts when using datasets. In our experience, datasets that require custom code to use often end up with limited reuse" — [HF Hub: Storage limits](https://huggingface.co/docs/hub/storage-limits)
- The `main` docs still carry a "dataset script" page framing scripts as an advanced option requiring `trust_remote_code=True`; it does not state a removal version — [datasets main docs: dataset_script](https://huggingface.co/docs/datasets/main/en/dataset_script). (Conflict: the release notes are authoritative; treat scripts as unusable with current `datasets`.)

Dataset Viewer / Data Studio
- "enabled by default for all public datasets. It is also available for private datasets owned by a PRO user or a Team or Enterprise organization" — [HF Hub: Uploading datasets](https://huggingface.co/docs/hub/datasets-adding), [HF Hub: Configure the Dataset Viewer](https://huggingface.co/docs/hub/datasets-viewer-configure)
- Table pages of 100 rows; column histograms; filter; case-insensitive search over string columns (including nested); SQL console (DuckDB); shareable row URLs (`…/viewer/<subset>/<split>?p=2&row=241`); iframe embed at `https://huggingface.co/datasets/<ns>/<name>/embed/viewer` — [HF Hub: Data Studio](https://huggingface.co/docs/hub/datasets-viewer)
- Size behaviour: "the first 5GB of every dataset are auto-converted to the Parquet format (unless it was already a Parquet dataset)"; for Parquet datasets the viewer shows everything but sort/filter/search only on the first 5 GB; for >5 GB non-Parquet only the first 5 GB; the `parquet-converter` bot opens a discussion; Parquet files are listed at `https://huggingface.co/api/datasets/<repo>/parquet` and under `refs/convert/parquet` — [HF Hub: Data Studio](https://huggingface.co/docs/hub/datasets-viewer)
- Disable with `viewer: false` in the YAML — [HF Hub: Configure the Dataset Viewer](https://huggingface.co/docs/hub/datasets-viewer-configure)
- Community reports (unverified official limits) of audio-Parquet failures: "Scan size limit exceeded … limit is 300000000 bytes" and "Rows from parquet row groups are too big to be read: 470.70 MiB (max=286.10 MiB)", with the fix being smaller row groups / page index — [vibravox discussion](https://huggingface.co:443/datasets/Cnam-LMSSC/vibravox/discussions/3), [jam-alt discussion](https://huggingface.co/datasets/audioshake/jam-alt/discussions/1) (attribution of which message appears on which thread comes from a search summary and was not re-checked)

Upload APIs
- `create_repo("ns/test-dataset", repo_type="dataset")`; visibility at creation via `create_repo("ns/x", visibility="private")` or CLI `hf repos create ns/x --repo-type dataset --private`; change later with `update_repo_settings(repo_id=…, private=True)` / `hf repos settings ns/x --private true`; gating via `api.update_repo_settings(repo_id=…, gated="auto")` / `hf repos settings ns/x --gated auto`; rename/transfer with `move_repo(from_id, to_id)` — [huggingface_hub: Create and manage a repository](https://huggingface.co/docs/huggingface_hub/guides/repository)
- `api.upload_file(path_or_fileobj=…, path_in_repo="README.md", repo_id="ns/test-dataset", repo_type="dataset")`; `api.upload_folder(folder_path=…, repo_id=…, repo_type="dataset", path_in_repo=…, allow_patterns=…, ignore_patterns=…, delete_patterns=…)`; root `.gitignore` is honoured — [huggingface_hub: Upload files](https://huggingface.co/docs/huggingface_hub/guides/upload)
- With `hf_xet` installed (default since `huggingface_hub` 0.32.0) `upload_folder` streams: "small folders are uploaded in a single commit, while folders with many files are automatically split into several commits"; "Resumable: … simply re-run the same call. Files already committed are detected and skipped"; follow-up commits get " (part 2)" suffixes; with `create_pr=True` re-run using `revision="refs/pr/N"`; `HF_XET_HIGH_PERFORMANCE=1` for max throughput (`HF_HUB_ENABLE_HF_TRANSFER` is obsolete) — [huggingface_hub: Upload files](https://huggingface.co/docs/huggingface_hub/guides/upload)
- CLI: `hf upload <repo_id> <local_path> <path_in_repo>`; `hf upload HuggingFaceM4/Docmatix --repo-type=dataset /path`; `hf://datasets/ns/name@branch/path` URIs — [huggingface_hub: Upload files](https://huggingface.co/docs/huggingface_hub/guides/upload)
- Low level: `create_commit(repo_id, operations=[CommitOperationAdd(path_in_repo, path_or_fileobj), CommitOperationDelete(path_in_repo), CommitOperationCopy(src_path_in_repo, path_in_repo)], commit_message=…)`; `preupload_lfs_files` for in-memory shards before a single commit; `run_as_future=True` for background uploads; `copy_files("hf://datasets/a/x/data/", "hf://datasets/a/y/data/")` server-side — [huggingface_hub: Upload files](https://huggingface.co/docs/huggingface_hub/guides/upload)
- The current upload guide no longer presents a separate `upload_large_folder` recipe; "`upload_folder()` and the `hf upload` command are the go-to solutions to upload files to the Hub, including for very large folders" — [huggingface_hub: Upload files](https://huggingface.co/docs/huggingface_hub/guides/upload)

Storage, Xet, limits
- Plans: free user/org = "Best-effort" public storage, 100 GB private; PRO = up to 10 TB public, 1 TB private + pay-as-you-go; public add-on $12/TB/month; private PAYG $18/TB/month base — [HF Hub: Storage limits](https://huggingface.co/docs/hub/storage-limits)
- Repo recommendations: files per repo <100k; "The maximum number of files per folder cannot exceed 10k files per folder"; file size <200 GB recommended, "500GB is the hard limit for a single file size"; commits <100 files (auto-split by `upload_folder`); 60 s HTTP timeout per commit request; "no per-repo size limit for models and datasets, but uploads count against your account's total storage quota" — [HF Hub: Storage limits](https://huggingface.co/docs/hub/storage-limits)
- Requirements for hosting datasets: a dataset card, intent for community reuse, well-integrated formats (Parquet/WebDataset), no custom loading scripts; storage grants exist for high-impact open work (contact datasets@huggingface.co) — [HF Hub: Storage limits](https://huggingface.co/docs/hub/storage-limits)
- Xet "enables chunk-level deduplication, smaller uploads, and faster downloads than Git LFS"; Git LFS remains supported; large files are pointer files identified via `.gitattributes` — [HF Hub: Xet storage](https://huggingface.co/docs/hub/xet/index). `hf_xet` chunks files, dedups across known chunks, uploads "xorbs" to a content-addressable service — [huggingface_hub: Upload files](https://huggingface.co/docs/huggingface_hub/guides/upload)

Gated datasets
- Enabled in repo settings ("Enable Access request"); automatic vs manual approval; requests are per user, share username + email unless the author opts out; custom form via `extra_gated_fields` (types `text`, `checkbox`, `date_picker`, `country`, `select` with `options`), `extra_gated_prompt`, `extra_gated_heading`, `extra_gated_description`, `extra_gated_button_content`; `extra_gated_eu_disallowed: true` (only when `gated: true`) — [HF Hub: Gated datasets](https://huggingface.co/docs/hub/datasets-gated)
- Review via UI or API (`GET /api/datasets/{repo_id}/user-access-request/{pending|accepted|rejected|reset}`, `POST …/handle`, `POST …/grant`) and Python (`list_pending_access_requests`, `accept_access_request`, `reject_access_request`, `grant_access`); downloadable JSON access report; users must `hf auth login` or pass `token` to `load_dataset` — [HF Hub: Gated datasets](https://huggingface.co/docs/hub/datasets-gated)

DOI
- "Generate DOI" button in model/dataset settings; you acknowledge "that some features on the hub will be restrained and some of your information (your full name) will be transferred to our partner DataCite"; author list can be personalised; a new DOI can be generated for a new revision ("the previous version of the DOI gets outdated"); repos with DOIs "may only be deleted, renamed and changed their visibility upon filing a request with our support" — [HF Hub: DOI](https://huggingface.co/docs/hub/doi), [HF blog: Introducing DOI](https://huggingface.co/blog/introducing-doi)

Croissant
- "The dataset viewer automatically generates the metadata in Croissant format (JSON-LD) for every dataset on the Hugging Face Hub … available for all the datasets that can be converted to Parquet format"; endpoint `https://huggingface.co/api/datasets/<repo>/croissant` (wraps `datasets-server.huggingface.co/croissant-crumbs` and enriches with Hub metadata); the output's `license`, `keywords` (tags, task categories, size category, language, licence), `creator`, `description`, `alternateName`, `url` come from the card; each config becomes a `cr:RecordSet` whose fields point at `parquet-files-for-config-<name>` — [dataset-viewer: Croissant](https://huggingface.co/docs/dataset-viewer/croissant)

Versioning and loading
- `create_tag("bigcode/the-stack", repo_type="dataset", revision="v0.1-release", tag="v0.1.1", tag_message="…")`; `create_branch(...)`; `list_repo_refs(repo, repo_type="dataset")` returns branches, `converts` (e.g. `refs/convert/parquet`) and tags; CLI `hf repos tag create <repo> v1.0 --repo-type dataset -m "…"` — [huggingface_hub: Create and manage a repository](https://huggingface.co/docs/huggingface_hub/guides/repository)
- `load_dataset("ns/repo", "subset_name", split="train")`; with several configs and no default, "you must explicitly select one … 🤗 Datasets will raise a `ValueError`"; `get_dataset_config_names(repo)`, `get_dataset_split_names(repo)`, `load_dataset_builder(repo).info.features` — [datasets: Load a dataset from the Hub](https://huggingface.co/docs/datasets/load_hub)
- Evaluation records on the Hub refer to a dataset by `dataset_config`, `dataset_split`, and `dataset_revision` ("The revision (AKA Git Sha) of the dataset used in `load_dataset()`") — [huggingface_hub cards reference: EvalResult](https://huggingface.co/docs/huggingface_hub/package_reference/cards)

- Because the Hub only recognises configured data files, `symbolic/` (MusicXML/MIDI/PDF) should be shipped as plain files with an `index.jsonl` manifest (which CAN be a viewer config) and fetched with `hf_hub_download`/`snapshot_download`; this mirrors how MAESTRO ships MIDI beside a metadata CSV (see KQ4).
- Order of operations for tonight: `create_repo(..., repo_type="dataset", visibility="private")` → `upload_folder` (resumable) → check Data Studio renders every config → fix YAML with `metadata_update` → `create_tag(tag="v1.0.0")` → `update_repo_settings(private=False)` (or `gated="auto"` if you want contact info) → "Generate DOI" (irreversible: locks delete/rename/visibility) → verify `/api/datasets/<repo>/croissant` returns the licence and record sets.
- Minting the DOI AFTER the public switch avoids a support ticket: DOI locks visibility changes.
- Keep every large JSONL < 10 MB or convert to Parquet; otherwise UI uploads silently skip it (the Python path with Xet handles it, but Parquet also gets the viewer's filter/SQL features).
- Loading for users becomes: `load_dataset("ns/qaraamigen-somali-music-research", "synth_benchmark", split="test", revision="v1.0.0")`.

## Key Question 2 — Dataset card best practice: HF template, Datasheets for Datasets, CARE, consent, documenting exclusions and limitations, model-output provenance

### Takeaway
The HF template already mirrors Datasheets' seven sections (motivation, composition, collection, preprocessing, uses, distribution, maintenance); a reference-grade card answers those questions explicitly, names what was EXCLUDED and why (here: all archival/Harvard/oud/`.band` audio), records inter-annotator or validation statistics, and for synthetic/model-output data records the full generation recipe per row. CARE adds a people-and-purpose layer (collective benefit, authority to control, responsibility, ethics) that FAIR lacks; for a diaspora-built Somali dataset that means stating who benefits, who controls, and how community members can object or contribute.

### Cited Findings
- HF default dataset-card template sections: Dataset Card for {{pretty_name}} → Dataset Details (Description; Sources: repo/paper/demo) → Uses (Direct Use; Out-of-Scope Use) → Dataset Structure ("The fields, how splits were made, and how data points relate") → Dataset Creation (Curation Rationale; Source Data: Data Collection and Processing, Who are the source data producers?; Annotations: Annotation process incl. "inter-annotator statistics", Who are the annotators?; Personal and Sensitive Information) → Bias, Risks, and Limitations (Recommendations) → Citation (BibTeX + APA) → Glossary → More Information → Dataset Card Authors → Dataset Card Contact; template variables include `curators`, `funded_by`, `shared_by` — [huggingface_hub datasetcard_template.md](https://raw.githubusercontent.com/huggingface/huggingface_hub/main/src/huggingface_hub/templates/datasetcard_template.md)
- Hub guidance: write "what are the use cases and limitations, where the data comes from, what are important ethical considerations"; "Import dataset card template" link in the editor; example card `abisee/cnn_dailymail` — [HF Hub: Uploading datasets](https://huggingface.co/docs/hub/datasets-adding)
- Datasheets for Datasets (Gebru et al.) questions, by section — Motivation: "For what purpose was the dataset created? - CARE Principles (Carroll et al. 2020): "Indigenous data must facilitate collective benefit for Indigenous Peoples to achieve inclusive development and innovation"; "Recognition of these rights bolsters Indigenous Peoples' authority to control and govern such data"; "there is a responsibility to nurture respectful relationships with Indigenous Peoples from whom the data originate"; "Paramount to ethics in data practices is representation and participation of Indigenous Peoples"; "The CARE Principles are designed to complement the FAIR Principles" — FAIR centres data, CARE extends to the "people" and "purpose" for which data exist — [Carroll et al., Data Science Journal 2020](https://datascience.codata.org/articles/10.5334/dsj-2020-043)

- Precedents for documenting what is NOT shipped: MusicCaps distributes "No audio … a CSV of YouTube IDs and start/end timestamps. - Precedent for errata/versions: MAESTRO V1/V2/V3 are mutually incompatible and the page asks users to "specify the dataset version they used" — [MAESTRO](https://magenta.tensorflow.org/datasets/maestro); MedleyDB keeps `ERRATA.md` listing known audio and metadata issues — [marl/medleydb](https://github.com/marl/medleydb); Slakh2100 "redux" moved duplicate-MIDI tracks to an `omitted` directory and advises not to use them for transcription training — [Slakh2100 redux (Zenodo)](https://zenodo.org/records/4599666)
- Precedent for annotator documentation: vocadito records two full note annotations by two trained musicians, reports inter-annotator agreement (Acc 0.83 ± 0.08, F 0.64 ± 0.13, F-no-offset 0.74 ± 0.09), anonymises singer IDs and documents recording devices (phones, laptop mics) and languages — [vocadito (ar5iv)](https://ar5iv.labs.arxiv.org/html/2110.05580)
- Kiñit (EMIR) dataset: 600 recordings (162 Tizita, 144 Bati, 147 Ambassel, 147 Anchihoye) labelled by five expert judges; "each Kiñit uses its own pentatonic scale and also has its own stylistic characteristics" — [Retta et al., arXiv 2201.08448](https://arxiv.org/abs/2201.08448) (search snippet; full paper not fetched)
- Generative-model usage caveats that belong in the card: MusicGen "should not be used on downstream applications without further risk evaluation and mitigation" and "should not be used to intentionally create or disseminate music pieces" that could offend — [facebook/musicgen-large](https://huggingface.co/facebook/musicgen-large); ACE-Step: "we encourage users to verify the originality of generated works, clearly disclose AI involvement", "obtain appropriate permissions when adapting protected styles or materials", risk of "unintentional copyright infringement due to stylistic similarity" — [ace-step/ACE-Step README](https://github.com/ace-step/ACE-Step)

### Inferences
- Map the card to Datasheets explicitly: add a "Datasheet" appendix or use the template headings with the Datasheets questions as bold prompts; reviewers recognise the form.
- An "Excluded material" subsection is the honest core of this card: list each excluded source class (Harvard/Aryette cassettes, Ahmed Ilkacase oud recordings, `.band` imports, internet-scraped oud/mix), the reason (rights per `docs/DATA_PROVENANCE.md`), and what IS present that was influenced by them (adapters trained on them produced the generated clips). Follow the OTMM/MusicCaps pattern: ship identifiers/derived artefacts, never the audio.
- Consent documentation: for the glossary and any musician-corrected packs, record who contributed (role, not PII unless agreed), when, under which licence they released their contribution, and the CARE-style statement of collective benefit and authority to control (a named contact and takedown route). For model outputs trained on rights-restricted sources, say so plainly in "Source Data → Who are the source data producers?" and in "Bias, Risks and Limitations" (style transfer from unreleased recordings).
- Model-output provenance schema per row (no published standard found; synthesis of Datasheets' "software available"/"raw data saved" questions plus MusicGen/ACE-Step disclosure guidance): `model_id` (Hub id, e.g. `facebook/musicgen-large`), `model_revision`, `adapter_name`, `adapter_sha256` or run id, `adapter_step`, `prompt`, `negative_prompt`, `seed`, `duration_s`, `sampling_rate`, `cfg`, `temperature`, `top_k`, `generation_date` (ISO 8601), `generator_commit` (git SHA of your service), `postprocessing` (loudness normalisation target, codec, bitrate), `metrics` (`spectral_flatness`, `pcs`, `voiced_ratio`, `mert_nn_sim`, `fad_*`), `rights_class`, `listening_votes`. Keep the seed-determinism proof (`PROOF_OF_GENERATION.md`) linked from the card.
- State known limitations of the generated audio honestly (your own 2026-09-19 diagnosis: SFT adapters add noise, spectral flatness 0.02–0.07 vs 0.005 base); Sturm's GTZAN lesson is that undocumented faults, not faults per se, destroy comparability.

## Key Question 3 — Licensing: CC variants, CC0, ODC-By; licences on AI-generated audio (MusicGen CC-BY-NC weights, ACE-Step MIT/Apache); mixed-licence datasets; what communities expect

### Takeaway
Hub identifiers exist for every option (`cc0-1.0`, `cc-by-4.0`, `cc-by-sa-4.0`, `cc-by-nc-4.0`, `cc-by-nc-sa-4.0`, `odc-by`, `pddl`, `other` + `license_name`/`license_link`) and `license` may be a list. CC 4.0 licences explicitly cover databases and sui generis database rights, so CC BY 4.0 is the community default for annotations, metadata and glossaries (vocadito, NSynth, Slakh, FMA metadata), with CC BY-SA for caption corpora (MusicCaps, Song Describer) and CC BY-NC-SA where third-party recordings are involved (MAESTRO, MedleyDB, Saraga, OTMM, MTG-Jamendo metadata). For AI-generated audio the copyright position is unsettled: the US Copyright Office (Jan 2025) says purely prompt-driven outputs are not protected, which means a CC licence on such clips may have nothing to attach to; MusicGen's weights are CC-BY-NC 4.0 with no statement on outputs, while ACE-Step 1.5 is MIT and its card says generated music may be used commercially.

### Cited Findings
- Hub licence identifiers (exact strings): `cc0-1.0`, `cc-by-4.0`, `cc-by-sa-4.0`, `cc-by-nc-4.0`, `cc-by-nd-4.0`, `cc-by-nc-sa-4.0`, `cc-by-nc-nd-4.0`, `cc` (family), `odc-by`, `odbl`, `pddl`, `cdla-permissive-2.0`, `cdla-sharing-1.0`, `mit`, `apache-2.0`, `c-uda`, `unknown`, `other`; "In case of `license: other` please add the license's text to a `LICENSE` file inside your repo … and set a name for it in `license_name`" — [HF Hub: Licenses](https://huggingface.co/docs/hub/repositories-licenses)
- `license` in `DatasetCardData` is `str | list[str]` ("License(s) of this dataset") — [huggingface_hub cards reference](https://huggingface.co/docs/huggingface_hub/package_reference/cards)
- Creative Commons FAQ: "Yes. CC licenses can be used on databases"; "In the 4.0 license suite, applicable sui generis database rights are licensed under the same license conditions as copyright"; "CC0 is not a license; it is a public domain dedication"; the Public Domain Mark is "a tool for marking a work that is in the worldwide public domain" and "is not legally operative"; "you cannot remove a work from the public domain by applying a CC license to it"; a work can be public domain "because the work did not meet the applicable standards for copyrightability"; for CC works inside a dataset, "the license conditions must be respected … providing the required attribution information in a way that is reasonable under the circumstances … in some cases that may be as simple as providing a link"; "The licenses grant permission for reuse in any situation that requires permission under copyright" — [Creative Commons FAQ](https://creativecommons.org/faq/)

### Inferences
- Per-subset licensing that matches both the rights situation and community expectations:
  - `glossary`, `evaluation` records, `synth_benchmark` (your own synthesis + ground truth), `symbolic` (your own engraving/MIDI) → **CC BY 4.0** (Hub `cc-by-4.0`); CC0 is defensible for the glossary if you want maximal reuse (PanLex precedent) but CC BY keeps the attribution the application needs.
  - `generated` clips from **MusicGen adapters** → the weights are CC-BY-NC; nothing in the licence or card addresses outputs, and the LoRA adapters were trained on rights-restricted audio. The conservative choice is to publish those clips under **CC BY-NC 4.0** (or CC BY-NC-SA) with an explicit "research use" note, and to say in the card that copyright in purely machine-generated audio is doubtful under US law so the licence functions as terms of use rather than a copyright grant.
  - `generated` clips from **ACE-Step 1.5** → the card permits commercial use of outputs; CC BY 4.0 is defensible, but again flag that the clips may not be copyrightable and that the LoRA was trained on `clean_oud` (own rights) — document which.
  - Declare `license: [cc-by-4.0, cc-by-nc-4.0]` in the header and a table in the card mapping subset → licence → rationale, as MTG-Jamendo/FMA do with per-track licence files; add `rights_class` and `licence` columns in each `metadata.jsonl` so the licence travels with the row.
- ODC-By (`odc-by`) is the data-specific alternative to CC BY for databases; since CC 4.0 already licenses sui generis database rights, CC BY 4.0 is sufficient and far more recognised in MIR (no reference MIR dataset above uses ODC-By).
- Avoid `-ND`: it blocks the derivative uses (resampling, segmenting, feature extraction) that make a dataset useful; avoid `-SA` for the benchmark unless you want to force downstream datasets to inherit it (MusicCaps/Song Describer chose SA for captions, which is why their re-users ship captions separately).
- Say in the card who claims what: Khalid/QaraamiGen asserts rights in the selection, arrangement, metadata, glossary, annotations and synthesis code; it makes no copyright claim over purely generated waveforms beyond the licence-as-terms-of-use.

## Key Question 4 — Reference MIR datasets and culturally specific corpora: what made them reference-grade; metadata schemas for scale/mode/tonic, metre, form, instrumentation, lyrics language

### Takeaway
Reference datasets share: a stable identifier scheme (MusicBrainz IDs, track IDs), one metadata table with a documented schema, canonical splits designed against leakage, shipped baselines, a permanent DOI'd host, a loader (mirdata or `datasets`), versioned errata, and a paper. Culturally specific corpora (CompMusic/Saraga/OTMM, Kiñit, dastgāh, Meertens) add tradition-native annotations — tonic in Hz, mode label (rāga/makam/kiñit/dastgāh), rhythmic-cycle markers (sama/usul/tāla), section names, phrases with solfège, lyrics with script and romanisation — and are honest about shipping derived features instead of audio when rights block distribution.

### Cited Findings

Culturally specific corpora
- CompMusic corpora cover Carnatic, Hindustani, Turkish makam, Beijing opera (jingju) and Arab-Andalusian music; per tradition they hold editorial metadata on MusicBrainz plus: Carnatic/Hindustani — lyrics, scores, rāgas, tālas, forms, compositions; Turkish makam — MusicXML/text/MIDI scores, makams, usuls, forms; Beijing opera — metadata "with Chinese script and Hanyu Pinyin romanization", lyrics, scores, role types and two main modes; Arab-Andalusian — nawba, tab', mizan, form and "section start/end timestamps"; access via Dunya and its API using MusicBrainz recording IDs — [CompMusic corpora](https://compmusic.upf.edu/corpora)
- Saraga (Carnatic 249 recordings, 52.7 h, 64 artists, 202 compositions, 96 rāgas, 10 tālas; Hindustani 108 recordings, 43.6 h, 61 rāgas, 9 tālas): annotations = tonic, pitch track, vocal pitch (168 Carnatic multitracks), sama, tempo, sections, melodic phrases; metadata fields rāga, tāla, laya (Hindustani), form, work; "Editorial metadata is kept on MusicBrainz, and each recording is identified by its MusicBrainz ID"; git repo holds a static metadata dump with md5 checksums — [Saraga companion page](https://mtg.github.io/saraga/)

- MTG-Jamendo: >55,000 full tracks, 195 tags (genre 95, instrument 41, mood/theme 59); per-track `track_id, artist_id, album_id, path, duration, tags`; splits 0–4 in `data/splits`; 320 kbps MP3 plus low-bitrate mono; baselines in `results/ml4md2019` (5 splits × 5 tag sets) and `results/mediaeval2019`; Bogdanov et al., ICML 2019 ML4MD workshop — [MTG/mtg-jamendo-dataset](https://github.com/MTG/mtg-jamendo-dataset)
- FMA: subsets small (8,000 × 30 s, 8 balanced genres), medium (25,000, 16 genres), large (106,574 × 30 s, 161 genres), full (untrimmed, 879 GiB); `tracks.csv`, `genres.csv` (hierarchy), `features.csv` (librosa), `echonest.csv`; code MIT, metadata CC BY 4.0, audio per-artist CC; Defferrard et al., ISMIR 2017 — [mdeff/fma](https://github.com/mdeff/fma)
- Slakh2100 redux: 2,100 tracks, 187 instrument patches in 34 classes, ~145 h; rendered from Lakh MIDI with "professional-grade sample-based virtual instruments"; `TrackXXXXX/` with mixture, per-source audio, MIDI and `metadata.yaml`; FLAC mono 44.1 kHz 16-bit; duplicates moved to `omitted`; CC BY 4.0; Manilow et al., WASPAA 2019 — [Zenodo 4599666](https://zenodo.org/records/4599666)
- MUSDB18: 150 tracks (~10 h), train 100 / test 50; stems vocals/drums/bass/other; sources DSD100 100, MedleyDB 46, Native Instruments 2, Easton Ellises 2; `.stem.mp4` AAC 256 kbps 44.1 kHz (mixture band-limited ~16 kHz) and MUSDB18-HQ WAV; DOIs 10.5281/zenodo.1117372 and 10.5281/zenodo.3338373; manual access check; museval (BSSEval v4) — [sigsep MUSDB18](https://sigsep.github.io/datasets/musdb.html)
- MedleyDB: 122 multitracks (+74 in v2 = 196), melody f0 for 108, instrument activations and genre for 122; 105 full tracks + 17 excerpts (7:17 h); WAV 44.1 kHz 16-bit; genres Singer/Songwriter, Classical, Rock, World/Folk, Fusion, Jazz, Pop, Musical Theatre, Rap; audio on Zenodo after "a quick permission request"; Bittner et al., ISMIR 2014 — [MedleyDB site](https://medleydb.weebly.com/); melody definitions: melody1 "the pitch of the single most predominant source", melody2 "the pitch of the predominant source for each point in time", melody3 "the pitch of any melodic source. Allows for more than one f0 value at a time"; CSV time s + frequency Hz (0 = unvoiced); metadata `artist, title, genre, is_excerpt, is_instrumental, n_sources`; annotations repo keeps `ERRATA.md` — [mirdata medleydb_melody](https://raw.githubusercontent.com/mir-dataset-loaders/mirdata/master/mirdata/datasets/medleydb_melody.py), [marl/medleydb](https://github.com/marl/medleydb)
- vocadito: 40 excerpts (10–40 s) of solo monophonic singing by ~29 singers in 7 languages recorded on phones/laptop mics; 44.1 kHz 16-bit mono WAV; f0 by one annotator in Tony (pYIN seed, manually corrected); notes by two annotators in Tony, pitch not quantised to semitones; lyrics transcribed as sung in Latin script (Chinese tracks with characters + pinyin), line = phrase, blank line = section; metadata CSV `track_id, singer_id, average_pitch, language`; f0 CSV = time, Hz (0 unvoiced); notes CSV = onset s, pitch Hz, duration s (`notesA1`/`notesA2`); baselines: Vocano notes (Acc 0.55, F 0.43–0.49, Fno 0.57–0.63), CREPE f0 (RPA 0.98, OA 0.82); CC BY 4.0; Zenodo 10.5281/zenodo.5578807; mirdata loader — [vocadito (ar5iv)](https://ar5iv.labs.arxiv.org/html/2110.05580), [mirdata vocadito loader](https://raw.githubusercontent.com/mir-dataset-loaders/mirdata/master/mirdata/datasets/vocadito.py), [Zenodo 5578807](https://zenodo.org/records/5578807)
- GTZAN's documented faults (see KQ2) are why it stopped being reference-grade: artist-filtered evaluation lowered accuracy for all five systems tested (SRCAM −22 points); the "perfect" classifier can reach only ~94.5 % — [Sturm 2013 (ar5iv)](https://ar5iv.labs.arxiv.org/html/1306.1461)

### Inferences
- Reference-grade checklist distilled from the above: (1) stable IDs + one metadata table with a published schema; (2) raw audio + text annotations in simple, documented formats (two-column time/Hz, onset/pitch/duration CSV) rather than bespoke binaries; (3) splits that are leakage-safe at the entity level (composition for MAESTRO, instrument for NSynth, artist for GTZAN's fix); (4) baselines and their numbers shipped with the data; (5) DOI'd permanent host plus a loader (mirdata or `datasets`); (6) versions with errata and an "omitted" policy; (7) explicit per-file licence; (8) honesty about non-shipped audio (OTMM, MusicCaps).
- A Somali/qaraami metadata schema that mirrors the CompMusic pattern (tradition-native terms with English glosses, one row per clip): `tonic_hz`, `scale_name_so` / `scale_name_en` (pentatonic mode name, both languages, glossary ID), `scale_degrees_cents` (fitted grid), `metre` (e.g. 6/8) and `rhythm_name_so`, `tempo_bpm`, `form_so`/`form_en`, `instrumentation` (list, glossary IDs: kaban/oud, …), `lyrics_language` (`so`, none for instrumental), `region`, `era`, `source_type` (`generated`, `synthetic`, `symbolic`), plus the generation-provenance fields from KQ2. Encode section/phrase annotations as the Saraga tab-separated `start, duration, label` convention so mirdata-style loaders are trivial.
- Because the Kiñit dataset showed that a four-class pentatonic-mode task with expert labels is publishable, a `synth_benchmark` with controlled scale/tonic ground truth is a credible first benchmark for Somali modes even without archival audio — provided the card says synthetic and gives the generation recipe.

### Gaps
- Serra 2014's exact corpus criteria (commonly cited as purpose, coverage, completeness, quality, reusability) could not be verified: the UPF repository returned an Anubis "Access Denied", the AES e-library returned 403, and the Saraga EMR article was blocked. The CompMusic corpora page does not name them.
- MedleyDB's full per-track YAML schema (stems/raw/components, `has_bleed`, `origin`), instrument taxonomy and activation-confidence format were not retrieved (project site and docs landing pages lack them).
- Essen Folksong Collection facts (count, EsAC fields, licence) were not retrieved: kern.humdrum.org returned 503, kern.ccarh.org and esac-data.org refused connections, Wikipedia had no page under that title.
- Beijing opera (jingju) and Arab-Andalusian corpus schemas were only seen at the summary level on the CompMusic page.
- African datasets other than the Ethiopian EMIR set (e.g., Nigerian/Ghanaian corpora) were not located before the search budget ran out.
- Iranian dataset details come from search snippets, not fetched papers.

## Key Question 5 — Benchmark design: canonical leakage-free splits, shipped baselines and scripts, mir_eval note-transcription conventions, FAD/CLAP conventions, leaderboards

### Takeaway
Use entity-level splits (song/composition/seed-family), ship the split column in the metadata and the baseline numbers plus the exact script, and evaluate notes with mir_eval's defaults (onset 50 ms, pitch 50 cents, offset 20 % of duration with a 50 ms floor, bipartite matching) reporting both with- and no-offset F-measures. For generated audio, FAD and CLAP scores are only comparable when the embedding checkpoint and reference set are stated; fadtk recommends against defaulting to MusicCaps as the reference for music and favours FMA-Pop, and VGGish-based FAD is now considered a classification-oriented legacy choice.

### Cited Findings
- mir_eval.transcription defaults: `onset_tolerance=0.05` ("50 ms"), `pitch_tolerance=50.0` ("50 cents"), `offset_ratio=0.2` ("the offset_tolerance will equal the ref_duration * 0.2"), `offset_min_tolerance=0.05` (used "whichever is greater"), `strict=False` (≤ comparisons); inputs are `(n,2)` interval arrays and pitch arrays in Hz; "mir_eval uses bipartite graph matching to find the optimal pairing of reference notes to estimated notes" (MIREX used greedy matching); "Every reference note is matched against at most one estimated note"; `offset_ratio=None` ignores offsets — [mir_eval transcription docs](https://mir-eval.readthedocs.io/latest/api/transcription.html)
- `evaluate()` score keys: always `Precision_no_offset, Recall_no_offset, F-measure_no_offset, Average_Overlap_Ratio_no_offset, Onset_Precision, Onset_Recall, Onset_F-measure`; when `offset_ratio` is not None also `Precision, Recall, F-measure, Average_Overlap_Ratio, Offset_Precision, Offset_Recall, Offset_F-measure`; `evaluate()` sets `offset_ratio` default 0.2 via `setdefault`; `validate()` raises on non-positive pitch values and on length mismatch — [mir_eval transcription.py](https://raw.githubusercontent.com/mir-evaluation/mir_eval/main/mir_eval/transcription.py)
- Human ceiling precedent: vocadito's two annotators agree at F 0.64 ± 0.13 (with offsets) and F-no-offset 0.74 ± 0.09, frame accuracy 0.83 ± 0.08 (10 ms frames, semitone match); quantising f0 to semitones gives only F 0.20 / Fno 0.38, i.e., notes are not derivable from f0 — [vocadito (ar5iv)](https://ar5iv.labs.arxiv.org/html/2110.05580)
- Split design precedents: MAESTRO keeps each composition in one split (962/137/177) — [MAESTRO](https://magenta.tensorflow.org/datasets/maestro); NSynth keeps instruments disjoint across train/valid/test — [NSynth](https://magenta.tensorflow.org/datasets/nsynth); Slakh redux moves duplicate-MIDI tracks to `omitted` because duplicates appeared "across splits with different audio" — [Zenodo 4599666](https://zenodo.org/records/4599666); GTZAN: random splits overstate performance, artist filtering lowers every system (SRCAM −22 points, MAPsCAT −25, MD −7) — [Sturm 2013 (ar5iv)](https://ar5iv.labs.arxiv.org/html/1306.1461); MTG-Jamendo publishes five splits and baseline results per split/tag set in the repo — [MTG/mtg-jamendo-dataset](https://github.com/MTG/mtg-jamendo-dataset); MUSDB18 fixes train 100 / test 50 and a reference toolkit (museval BSSEval v4) — [sigsep MUSDB18](https://sigsep.github.io/datasets/musdb.html)
- FAD tooling (fadtk): embeddings `clap-2023`, `clap-laion-audio`, `clap-laion-music`, `encodec-emb`, `MERT-v1-95M`, `vggish`, `dac-44kHz`, `cdpam`, `w2v2`, `hubert`, `wavlm`, `whisper`; CLI `fadtk <model_name> <baseline> <evaluation-set> [--inf/--indiv]` (`--inf` = FAD∞ extrapolation, `--indiv` = per-song scores "useful for finding outliers"); "advise against defaulting to MusicCaps without considering the research goal. For generative music, they recommend the FMA-Pop subset"; VGGish "is optimized for classification and may be less suitable for measuring quality"; Gui, Gamper, Braun, Emmanouilidou, ICASSP 2024; MIT — [microsoft/fadtk](https://github.com/microsoft/fadtk)
- Historical convention: MusicGen reported FAD with the official TensorFlow VGGish implementation against MusicCaps and a CLAP score as cosine similarity between text description and generated audio using the official pretrained CLAP — [Copet et al. 2023, arXiv 2306.05284](https://arxiv.org/pdf/2306.05284) (search snippet); a 2026 text-to-music challenge adopts the LAION CLAP music checkpoint for both FAD and CLAP score, citing best alignment with human preference — [arXiv 2605.21538](https://arxiv.org/pdf/2605.21538) (search snippet)
- Hub leaderboard plumbing: `EvalResult(task_type, dataset_type, dataset_name, metric_type, metric_value, dataset_config, dataset_split, dataset_revision, source_name, source_url)` → `model-index` in model cards; `train-eval-index` exists in dataset card metadata (`DatasetCardData.train_eval_index`) — [huggingface_hub cards reference](https://huggingface.co/docs/huggingface_hub/package_reference/cards)

### Inferences
- For `synth_benchmark`: write a `split` column (`test` only if it is purely an evaluation set, or `dev`/`test` by melody family so no melody appears in both); store notes as `onset_s, offset_s, pitch_hz` plus `midi` for readability (mir_eval needs intervals + Hz); ship `scripts/eval_notes.py` that calls `mir_eval.transcription.evaluate(ref_intervals, ref_pitches, est_intervals, est_pitches)` with defaults and prints both `F-measure` and `F-measure_no_offset`; publish your Qormada baseline numbers (the QORMADA_EVAL figures: vocadito note F1 0.687 vs annotators' 0.740; synthetic set F1 0.820) in a `results/` table with the dataset tag they were computed on.
- For `generated`: report per-clip automatic metrics already computed (spectral flatness, PCS, voiced ratio, MERT nearest-neighbour similarity) and, if you add FAD, state `fadtk` version, embedding (`clap-laion-music` for music), reference set (and its licence), and use `--indiv` to flag outliers; do not compare to VGGish/MusicCaps numbers from other papers.
- For listening-study records: keep the protocol fields already on record (paired, randomised order, hidden names, "neither" allowed) as columns, plus `listener_id` (anonymised), `trial_index`, `attention_check` flag — this is what makes the `/study` data a reusable benchmark.
- A leaderboard can be as simple as a `results/leaderboard.md` + `results/*.jsonl` with `dataset_revision` recorded; HF `model-index` lets model authors point back at your dataset config/split/revision.

### Gaps
- The exact FAD/CLAP conventions in the MusicGen paper and the 2026 challenge paper come from search snippets, not fetched full texts.
- mir_eval's melody-module conventions (voicing recall/false alarm, raw pitch accuracy at 50 cents) were not fetched this session (the old docs URL redirected); vocadito's CREPE baseline implies them.
- No fetched source documents a standard for seed-family or prompt-family leakage in generated-audio benchmarks; the recommendation above is an inference.

## Key Question 6 — Glossary/lexicon datasets on the Hub, Somali-language metadata alignment, music-terminology datasets

### Takeaway
Lexicon datasets on the Hub are flat tables keyed by a concept/meaning ID with one row per (language, expression) or per translation pair, released permissively (PanLex derivative under `cc0-1.0`, Somali parallel corpus `cc-by-4.0`), with `language:` lists in the YAML and per-language or per-pair configs. For Somali, both `so` (ISO 639-1) and `som` (ISO 639-3) appear on the Hub; the Hub accepts either, and a SomaliWeb survey counted roughly 250 "somali" datasets in April 2026, mostly speech, translation and instruction data. No Somali music-terminology dataset was found.

### Cited Findings
- PanLex-derived lexicon (`cointegrated/panlex-meanings`): YAML `license: cc0-1.0`, `task_categories: [translation]`, `size_categories: [10M<n<100M]`, a `language:` list of ISO 639 codes mirroring per-language configs (`config_name: ava` → one TSV per language; default config `data_files: "data/*.tsv"`); fields `id` (expression id), `langvar` (language-variety id), `txt`, `txt_degr` ("degraded (i.e. simplified to facilitate lookup) text"), `meaning` ("the column to join for obtaining synonyms (within a language) or translations (across languages)"), `langvar_uid` (e.g. `eng-000`, `eng-004`); "by joining per-language datasets by meaning ids, one can obtain a bilingual dictionary"; warns that multi-hop joins create false pairs because of polysemy — [cointegrated/panlex-meanings README](https://huggingface.co/datasets/cointegrated/panlex-meanings/raw/main/README.md)
- Other Hub lexicon examples (search snippets): MUSE bilingual dictionaries (110 ground-truth dictionaries, train/test word splits, polysemy accounted for) — [SEACrowd/muse](https://huggingface.co/datasets/SEACrowd/muse/blob/main/muse.py); FrancophonIA multilingual MARC 21 terms (accepted and tentative terms in six languages in parallel columns) — [FrancophonIA/Multilingual_Dictionary_ofMARC_21_Terms](https://huggingface.co/datasets/FrancophonIA/Multilingual_Dictionary_ofMARC_21_Terms); Termcat multidictionary — [FrancophonIA/Termcat_Multidictionary](https://huggingface.co/datasets/FrancophonIA/Termcat_Multidictionary/blob/main/README.md)
- Terminology standard: TBX (TermBase eXchange) is ISO 30042:2019, "the international standard for archiving and exchanging terminological information"; version 3 published 2019 with dialects TBX-Core, TBX-Min, TBX-Basic (TBX-Basic for tool import/export) — [tbxinfo.net](https://www.tbxinfo.net/)
- Somali on the Hub: `tufaax/en-so-parallel-clean-8k` — `language: [en, so]`, `license: cc-by-4.0`, `task_categories: [translation]`, `size_categories: [1K<n<10K]`, tags `en-so`, `parallel`; two string columns `en`, `so`; 8,912 pairs — [tufaax README](https://huggingface.co/datasets/tufaax/en-so-parallel-clean-8k/raw/main/README.md); `google/fleurs` lists Somali as `- som` and uses `so_so` as the `lang_id` label/config style; `license: cc-by-4.0` — [google/fleurs README](https://huggingface.co/datasets/google/fleurs/raw/main/README.md)
- Somali dataset landscape (search snippets): "A keyword search of the Hugging Face Hub for 'somali' returns roughly 250 datasets at time of writing (April 2026)", most being speech, translation or instruction data; SomaliWeb v1 ~819K documents, CC-BY-SA 4.0; `IbraahimLab/fineweb-somali` 4,910 BBC Somali documents (MIT); `FarmerlineML/somali_cleaned_dataset` 2,936 audio+transcription rows, ~2.79 GB, no declared licence, empty README — [SomaliWeb v1, arXiv 2605.18232](https://arxiv.org/pdf/2605.18232); `CohereForAI/aya_collection_language_split` has a Somali subset with train/validation/test — [aya_collection_language_split (somali)](https://huggingface.co/datasets/CohereForAI/aya_collection_language_split/commits/177afbbff8deb3a9384b45480fdf9108c54337eb/somali); `CIRAL/ciral` includes a `ciral-somali` folder — [CIRAL/ciral](https://huggingface.co/datasets/CIRAL/ciral/commits/main/ciral-somali); CulturaX maintainers confirmed "SO" = Somali, inherited from OSCAR and small — [CulturaX discussion 4](https://huggingface.co/datasets/uonlp/CulturaX/discussions/4); other Somali repos seen: `unkadlabs/qor-af-soomaali-frequency`, `SomaliDatasets/maay-maxaa-translation` — [qor-af-soomaali-frequency](https://huggingface.co/datasets/unkadlabs/qor-af-soomaali-frequency/discussions), [maay-maxaa-translation](https://huggingface.co/datasets/SomaliDatasets/maay-maxaa-translation/discussions)
- Hub language metadata rules: `language` codes may be ISO 639-1/2/3; `multilinguality` ∈ {`monolingual`, `multilingual`, `translation`, `other`}; `language_details` takes BCP-47 (e.g. `so-SO`) — [huggingface_hub DatasetCardData](https://huggingface.co/docs/huggingface_hub/package_reference/cards), [hub-docs/datasetcard.md](https://github.com/huggingface/hub-docs/blob/main/datasetcard.md?plain=1)

### Inferences
- Use `so` in `language:` (matches the ISO 639-1 instruction on the card page and the majority Somali text datasets) and add `language_details: [so-SO, en-US]` if dialect/region matters; `multilinguality: [multilingual]` for the whole dataset, and the glossary config can be tagged `translation` in the card body.
- Glossary schema (flat, Parquet/CSV; TBX-inspired concept → language → term, flattened to one row per term; one `concept_id` per sense, following PanLex's `meaning` join key): `concept_id`, `term_so`, `term_so_variants` (list), `term_en`, `pos`, `domain` (e.g. instrument, scale/mode, rhythm, form, performance practice), `definition_so`, `definition_en`, `example_so`, `example_en`, `related_concept_ids`, `source` (person/book/recording reference), `source_type` (`elicited`, `literature`, `transcribed`), `contributor_id`, `confidence` or `status` (`accepted`/`tentative`, as the MARC 21 dictionary does), `notes`, `licence`. Keep IDs stable across versions so audio metadata (`scale_concept_id`, `instrument_concept_ids`) can reference glossary rows.
- Provide the glossary both as the `glossary` config (viewer-friendly) and as an optional TBX-Basic export in `docs/` for terminologists; the Hub will not render TBX, so it is a supporting file only.
- Because no Somali music-terminology dataset exists on the Hub (as far as this search could tell), tag it `glossary`, `terminology`, `somali`, `music` and name the Somali terms in `pretty_name`/description to be findable.

### Gaps
- TBX element names (`conceptEntry`, `langSec`, `termSec`) and data categories were not confirmed from tbxinfo.net's landing page.
- No systematic Hub query for "Somali music" or "qaraami" datasets could be run after the search budget was exhausted; the "none found" statement rests on the SomaliWeb snippet and the datasets surfaced above.
- Whether the Hub validator rejects `so` and `som` appearing together, or warns on 639-3 codes, was not tested.
